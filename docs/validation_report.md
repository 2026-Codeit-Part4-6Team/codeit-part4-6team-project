## 1. Abstract — 초록

생성형 AI가 만든 광고 문구를 **사용자에게 보여주기 전에 자동으로 검증하는 함수 4종**을 설계·구현하고, 
자체 제작한 골든 데이터셋 67문항으로 성능을 측정했다.

핵심은 `check_regulation` 이다. 
표시광고법·식품표시광고법 조문 36개를 지식베이스로 구축하고, 
**키워드 스크리닝(1단) → 벡터 검색 + LLM 판정(2단)** 
2단 구조로 법률 위반을 판정한 뒤 **법에 맞는 대안 문구까지 생성**한다.

최종 실측(2026-08-28) 결과는 다음과 같다.

| 지표 | 목표 | 실측 | 판정 |
| --- | --- | --- | --- |
| 위반 차단률 (block recall) | 100% | **100%** | ✅ |
| 과잉 차단률 (over-block) | ≤ 10% | **0%** | ✅ |
| 대안 제시율 | 100% | **100%** | ✅ |
| 대안 유효성 (재검사 통과) | ≥ 95% | **100%** | ✅ |
| 표현 불변성 (invariance) | ≥ 95% | **98.8%** | ✅ |
| RAGAS-SCORE 종합 평가 지표 | ≥ 0.70 | **0.65** | ❌ |

6개 목표 중 5개를 달성했고, RAGAS-SCORE 종합 평가 지표만 미달이다. 
미달 원인은 §7에서 분석한다.

이 보고서가 주장하는 것은 "완벽한 검증기를 만들었다" 가 아니라
**"무엇을 못 하는지까지 숫자로 말할 수 있는 검증기를 만들었다"** 이다.

## 2. Introduction — 소개

### 2.1 문제

소상공인이 AI로 광고 문구를 만들면 이런 문장이 나온다.

> "우리 동네 **최고**의 카페, 이 **커피 한 잔이 피로를 풀어드립니다**"

두 군데가 법에 걸린다.

| 표현 | 위반 조항 | 성격 |
| --- | --- | --- |
| "최고" | 표시광고법 시행령 제3조 제1항 | 객관적 근거 없는 절대적 표현 |
| "피로를 풀어드립니다" | 식품표시광고법 제8조 제1항 제1호 | 식품의 질병 예방·치료 효능 표현 |

**문제는 소상공인이 이 사실을 모른다는 것이다.** 광고 대행사를 쓰면 걸러지지만,
직접 만들면 그대로 인쇄되어 가게 앞에 걸린다.

### 2.2 왜 LLM 프롬프트만으로는 부족한가

`copy_gen.py` 시스템 프롬프트에는 이미 금지 지시가 있다.

```
"'최고', '유일', '1등'처럼 근거 없는 과장 표현과
 질병 예방·치료 효능 표현은 쓰지 않는다."
```

그런데 **1차 E2E 테스트(2026-08-27) 진행 중 "완벽한" 이 그대로 LLM 모델 답변으로 생성됐다.**
질문에는 과장 표현이 없었다 — "코드잇 카페의 장점을 강조하는 광고 문구를 만들어줘".

> LLM은 지시를 확률적으로 따른다. **예방(프롬프트)만으로는 부족하고 사후 검증이 필요하다.**
> 이것이 검증 함수를 별도 계층으로 둔 이유다.

### 2.3 기여

1. 표시광고법·식품표시광고법 조문 **36개를 검색 가능한 KB로 구조화**
2. 키워드 스크리닝 + 벡터 검색 + LLM 판정 **2단 검증 파이프라인** 구현
3. 법률 위반 시 **차단에 그치지 않고 법에 맞는 대안 문구 생성** (유효성 100%)
4. 자체 골든 데이터셋 **67문항**과 **분류·검색·견고성 3계층 평가 체계** 구축
5. 지식베이스 없이 동작하는 **1단 폴백 모드**를 별도 측정해 성능 차이 정량화

## 3. Related Work — 기존 방식과 이 프로젝트의 위치

### 3.1 기존 접근 세 가지

| 방식 | 대표 사례 | 장점 | 한계 |
| --- | --- | --- | --- |
| **키워드 금칙어 필터** | 대부분의 커머스 광고 심사 | 빠름·비용 0 | 문맥을 모름. "최고급 원두"(허용)와 "최고의 카페"(위반)를 구분 못 함 |
| **범용 콘텐츠 모더레이션** | OpenAI Moderation API | 즉시 사용 | 폭력·성적 표현 중심. **국내 광고법을 모름** |
| **LLM 단독 판정** | GPT에 "이거 법에 걸려?" | 문맥 이해 | 근거를 지어냄(환각). 법률 조문 번호를 만들어낸다 |

### 3.2 해당 프로젝트 위치

세 가지 문제를 **각각 다른 층에서** 해결했다.

```
1단 키워드 스크리닝   →  명백한 법률 위반을 LLM 호출 0회로 즉시 차단 (비용·속도)
2단 벡터 검색        →  실제 법률 조문을 KB에서 가져온다 (환각 방지)
2단 LLM 판정        →  가져온 법률 조문을 근거로 문맥을 판단 (필터의 한계 극복)
```

특히 **법률 조문을 KB에서 직접 가져오는 것**이 핵심이다.
LLM에게 "표시광고법 몇 조야?"를 묻지 않고, 검색된 법률 조문을 프롬프트에 넣어 판정만 시킨다.
그 결과 **faithfulness 1.000** — 판정에 인용된 조문이 전부 KB에 실재한다.

### 3.3 RAGAS-SCORE 종합 평가 지표를 차용하되 그대로 쓰지 않은 이유

RAG 평가 표준인 RAGAS-SCORE(context recall/precision, faithfulness)를 종합 평가 지표로 채택했다.
다만 **`context_precision`은 우리 팀 프로젝트에 적합하지 않다** — §7.2에서 설명한다.

## 4. Method — 설계와 구현

### 4.1 검증 함수 4종과 배치 위치

| 함수 | 입력 | 위치 | 판정 |
| --- | --- | --- | --- |
| `check_input` | 사용자 질문 | 파이프라인 진입 직후 | 프롬프트 인젝션·불법 요청 |
| `check_regulation` | **생성된 카피** | 카피 생성 직후 | 표시광고법·식품표시광고법 |
| `check_output` | 최종 응답 텍스트 | 응답 조립 후 | 개인정보·민감정보 노출 |
| `self_check` | 응답 + 근거 | 최종 발행 직전 | 근거 유무·완결성 |

**챗봇별 연결은 다르다.**

| 함수 | 기본 챗봇 | 컨설턴트 챗봇 | 근거 |
| --- | --- | --- | --- |
| `check_input` | ✅ | ✅ | 사용자 질문은 양쪽 동일 |
| `check_regulation` | ✅ | **❌** | 아래 §4.2 |
| `check_output` | ✅ | ✅ | 양쪽 다 텍스트가 사용자에게 나감 |
| `self_check` | ✅ | ✅ | 양쪽 다 근거·완결성 필요 |

### 4.2 컨설턴트 챗봇에 법률 규제 검증 기능을 붙이지 않은 이유

> **이 판단은 발표에서 가장 많이 질문받을 지점이므로 근거를 명시한다.**

1. `check_regulation`의 입력은 **"생성된 카피"** 다. 컨설턴트는 카피를 만들지 않는다
   (전략 조언 = summary·actions·reasons).
2. 표시광고법은 **"광고"** 에 적용된다. 컨설팅 조언 자체는 광고가 아니다.
3. 컨설턴트 전략이 광고가 되는 경로는 **[이 전략으로 광고 만들기] 하나뿐**이며,
   그 결과물은 기본 챗봇 파이프라인의 `regulation_node` 함수를 통과한다.
4. 붙이면 warn 시 전략 재생성 루프가 생겨 LLM 호출이 늘고 팀 공용 $30 예산이 조기 소진된다.

**단, 컨설턴트가 "이 지역 최고 카페로 포지셔닝하세요" 같은 답변을 할 수 있으므로**
strategy SYSTEM_PROMPT 에 아래 한 줄을 추가한다.(LLM 모델 API 호출 0회·법률 규제 검증 노드 0개):
  "'최고'·'유일'·'1등' 같은 근거 없는 최상급 표현과 질병 예방·치료 효능 표현은 쓰지 않는다."

### 4.3 `check_regulation` 2단 구조

```
카피 입력
   │
   ├─[1단] 키워드 스크리닝 ─── 명백한 위반 패턴 매칭 (LLM 0회)
   │         │
   │         ├─ 확실한 위반 → 즉시 block, 법률 조문·대안 반환
   │         └─ 애매함 ─────┐
   │                        ▼
   └─[2단] 벡터 검색 (text-embedding-3-small, top-k=3)
             │              KB 36청크에서 관련 법률 조문 검색
             ▼
           LLM 판정 (gpt-5.4-mini, temperature 0)
             │   검색된 법률 조문만 근거로 사용 — 조문을 지어내지 않는다
             ▼
           action ∈ {pass, warn, block} + law + alternative
```

**설계 판단 3가지**

| # | 판단 | 이유 |
| --- | --- | --- |
| 1 | 1단에서 끝낼 수 있으면 2단을 안 탄다 | 명백한 불법 품목("마약 판매")에 LLM을 쓰는 것은 낭비다. **차단 시 LLM 호출 0회** |
| 2 | `law` 필드는 KB에서 직접 복사한다 | LLM이 법률 조문 번호를 만들어내는 것을 막는다 → faithfulness 1.000 |
| 3 | 대안 문구를 **재검사**한다 | 대안이 또 위반이면 의미가 없다. `_safe_alternative()`가 생성된 대안을 다시 `check_regulation`에 통과시킨다 |

### 4.4 지식베이스 구축

원문 법령을 **판정에 쓸 수 있는 단위**로 재구성했다.

| 항목 | 값 |
| --- | --- |
| 총 청크 | **36개** (REG-001 ~ REG-036) |
| 근거 법령 | 표시광고법 및 시행령, 식품표시광고법, 약사법, 상표법 등 |
| 임베딩 모델 | `text-embedding-3-small` (1536차원) |
| 인덱스 | NumPy 코사인 유사도 (`vectors.npy` + `meta.json`) |
| 무결성 | `source_sha256`로 KB 원본과 인덱스 정합성 검증 |

각 청크는 법률 조문 및 원문만이 아니라 **트리거 표현·허용 예시·대안 문구**를 함께 담는다.
검색된 청크를 그대로 프롬프트에 넣으면 LLM이 판정과 대안 생성을 한 번에 할 수 있다.

### 4.5 골든 데이터셋 설계

**67문항**을 직접 작성했다. 분포는 다음과 같다.

| 기대 판정 | 문항 수 | 비중 |
| --- | --- | --- |
| `warn` (경고 + 대안) | 33 | 49.3% |
| `block` (차단) | 20 | 29.9% |
| `pass` (통과) | 12 | 17.9% |
| `reject` (형식 오류) | 2 | 3.0% |

| 카테고리 | 문항 수 | 목적 |
| --- | --- | --- |
| `over_block_guard` | 12 | **정상 문구를 차단하지 않는지** 확인 |
| `illegal` | 10 | 불법 품목 차단 |
| `injection` | 8 | 프롬프트 인젝션 방어 |
| `exaggeration` | 8 | 과장·절대적 표현 |
| `medical` | 8 | 질병 예방·치료 효능 표현 |
| `coverage` | 7 | KB 법률 조문 커버리지 |
| `false_claim` / `deceptive` | 8 | 허위·기만 표시 |

> **`over_block_guard` 12문항이 설계의 핵심이다.**
> 차단률만 보면 "전부 차단"이 100%가 된다. 
> 정상 문구를 지키는 문항을 함께 두어야 그 착시가 깨진다.

## 5. Experiment Setup — 실험 환경

### 5.1 고정 조건

> **재현성을 위해 아래 조건을 모두 고정하고, 결과 파일에 함께 기록한다.**
> 조건이 하나라도 다르면 회차 간 비교를 하지 않는다.

| 항목 | 값 |
| --- | --- |
| 판정 모델 | `gpt-5.4-mini` |
| 판정 temperature | `0` |
| 임베딩 모델 | `text-embedding-3-small` |
| 검색 top-k | `3` (고정, 동적 k 비활성) |
| KB 청크 수 | `36` |
| 데이터셋 버전 | `refusal-v2-5d3628ae` (라벨 + 파일 해시) |
| 문항 수 | `67` |
| 측정 일시 | 2026-08-28 08:24 KST |

**`dataset_version`을 라벨+해시로 생성하는 이유**: 문항 내용만 고치고 버전 라벨을
올리는 것을 잊으면, 서로 다른 데이터셋의 결과를 같은 것으로 착각하게 된다.
파일 해시를 붙이면 그 사고가 구조적으로 불가능해진다.

### 5.2 두 가지 구성을 모두 측정한다

| 구성 | RAG | 설명 |
| --- | --- | --- |
| **정상** | 활성 | 1단 + 2단(벡터 검색 + LLM 판정) |
| **폴백** | 비활성 | 1단 키워드 스크리닝만 (KB·LLM 미사용) |

> 폴백 모드를 따로 측정하는 이유는 **"지식베이스가 없으면 성능이 얼마나 떨어지는가"**
> 를 숫자로 답하기 위해서다. 이 값이 없으면 KB 구축의 가치를 주장할 수 없다.

### 5.3 3계층 평가 지표

| 계층 | 지표 | 묻는 질문 |
| --- | --- | --- |
| **분류** | block recall, over-block rate, macro F1, safety score | 판정이 맞는가 |
| **검색** | context recall/precision, faithfulness, MRR, Hit@1, nDCG@3 | 근거를 제대로 찾는가 |
| **견고성** | invariance rate, alternative validity | 표현이 바뀌어도 같은 판정인가 |

### 5.4 견고성 측정 방법

**불변성(invariance)**: 같은 의미의 문장을 표현만 바꿔 입력했을 때 판정이 유지되는지 측정한다.

```
원문   "우리 가게가 최고입니다"
변형   "저희 매장이 최고예요" / "우리 집이 제일 좋습니다"
→ 셋 다 warn 이어야 한다
```

**대안 유효성**: 생성된 대안 문구를 `check_regulation`에 **다시 넣어** 통과하는지 확인한다.
대안이 또 위반이면 사용자에게 아무 도움이 안 된다.

## 7. Conclusion — 결론과 고찰

### 7.1 무엇을 확인했나

**① 프롬프트 예방만으로는 부족하다는 것을 실증했다.**

`copy_gen` 프롬프트에 이미 "'최고'·'유일'·'1등'을 쓰지 않는다"가 있었는데도
1차 E2E 테스트 진행 중 "완벽한"이 LLM 모델 답변으로 생성됐다. 사용자 질문에는 과장 표현이 전혀 없었다.
**LLM은 지시를 확률적으로 따르므로 사후 검증 계층이 필요하다** 
— 이것이 이 프로젝트의 가장 실용적인 발견이다.

**② 검증기의 가치는 "차단"이 아니라 "교정"에 있다.**

§6.3이 그 근거다. 차단률은 1단(키워드)만으로도 100%다. 
2단 RAG가 만드는 차이는 **대안 유효성 90.3% → 100%** 다. 
사용자에게 "이건 안 됩니다"만 말하는 것과
"이건 안 되지만 이렇게 쓰시면 됩니다"를 말하는 것의 차이가 곧 이 시스템의 가치다.

**③ 과잉 차단을 막는 데이터가 있어야 차단률이 의미를 갖는다.**

`over_block_guard` 12문항이 없었다면 "전부 차단"으로도 block recall 100%가 나온다.
정상 문구를 지키는 문항을 함께 설계한 것이 이 평가 체계의 핵심이다.

### 7.2 RAGAS-SCORE 종합 평가 지표 - 목표 점수 미달을 어떻게 볼 것인가

> **불리한 숫자를 먼저 설명한다.**

RAGAS-SCORE 종합 평가 점수는 0.6545로 목표 0.70에 미달했다. 
구성 요소를 보면 원인이 분명하다.

| 구성 지표 | 값 | 평가 |
| --- | --- | --- |
| context recall | 1.0000 | 필요한 법률 조문을 **빠짐없이 찾는다** |
| **faithfulness** | 1.0000 | 인용한 법률 조문이 **전부 KB에 실재한다** |
| **context precision** | **0.3871** | 검색 결과에 불필요한 법률 조문이 섞인다 |

**종합 평가 점수를 끌어내린 것은 `context_precision` 하나다.**

해당 지표는 "검색한 3개 중 실제로 판정에 쓰인 법률 조문의 비율"을 본다.
top-k=3으로 고정했으므로, 정답 법률 조문이 1개인 문항에서는 **최대 0.333** 이 상한이다.
0.3871은 그 상한에 근접한 값이다.

**두 가지 선택지가 있었다.**

| 선택 | 결과 |
| --- | --- |
| 동적 top-k (필요한 만큼만 검색) | precision은 오르지만, 실측 결과 **과잉 차단률이 8.3% → 25%로 악화** |
| top-k=3 고정 | precision은 낮지만 **과잉 차단 0%, 판정 정확도 100%** |

**후자를 선택했다.** 이 서비스에서 더 중요한 것은 검색 효율이 아니라 판정 정확도이기
때문이다. 정상 문구가 차단되면 사용자는 해당 서비스를 이용할 수 없다.

> 즉 **RAGAS-SCORE 종합 평가 점수 미달은 실패가 아니라 트레이드오프의 결과다.**
> 다만 "목표를 세웠고 못 미쳤다"는 사실 자체는 그대로 기록한다 —
> 목표치를 사후에 낮추면 그 이후의 모든 수치가 신뢰를 잃는다.

### 7.3 알려진 한계

**① KB 커버리지 94.4% — 구조적으로 도달 불가능한 법률 조문 2개**

REG-033·REG-036은 다른 법률 조문의 트리거 표현이 먼저 매칭되어 단독으로 검색 1위가 되지 않는다. 
해당 법률 조문 자체가 잘못된 것이 아니라 **트리거 우선순위가 겹치는 구조적 한계**다.
따라서 "36조문 중 34조문(94.4%) 커버" 가 아니라
**"도달 가능한 34조문에 대해 100% 커버"** 로 보고하는 것이 정확하다.

**② temperature=0이 재현성을 보장하지 않는다**

동일 입력을 5회 반복 측정한 결과, 한 문항(R-055 골든 데이터셋 문항)에서 판정이 흔들렸다 —
`pass` 2회 / `warn` 3회. temperature를 0으로 두어도 OpenAI API는 완전 결정론적이지 않다.
따라서 **보수적으로 warn(3회)을 기준으로 보고**했다. 
실제 과잉 차단률은 0%~1.5% 사이일 수 있다.

**③ 두 측정 사이에 데이터셋이 바뀌었다**

§6.2의 개선 추이는 데이터셋 보완이 섞여 있다. 
로직 개선분만 분리하려면 동일 `dataset_version`으로 재측정해야 한다.

**④ 이미지 안의 텍스트는 검증하지 않는다**

`check_regulation`은 카피 문자열만 본다. 
생성된 이미지에 박힌 문구 (예: "한 잔 무료!")는 검증 범위 밖이다. 
프롬프트 지시로 예방하고 있으나 **사후 검증은 없다** — OCR 기반 검증이 후속 과제다.

### 7.4 만약 다시 한다면

**① 데이터셋을 먼저 고정하고 로직을 고쳤을 것이다.**
지금은 둘이 함께 움직여 개선폭을 정확히 귀속시킬 수 없다.

**② `context_precision` 목표치를 처음부터 다르게 잡았을 것이다.**
top-k 고정 구조에서 이 지표의 상한은 이론적으로 정해진다. 
상한을 모르고 목표를 세운 것이 미달의 절반쯤 되는 원인이다.

**③ 이미지 검증을 처음부터 범위에 넣었을 것이다.**
텍스트만 검증하고 이미지를 두면, 사용자가 실제로 게시하는 최종 산출물의 절반이 검증을 안 거친다.

### 7.5 이 작업이 남긴 것

숫자보다 중요한 것은 **"모른다는 것을 아는 상태"** 에 도달했다는 점이다.

작업 초기에는 검증기가 잘 동작하는지 물으면 "잘 되는 것 같다"고 답했다.
지금은 이렇게 답할 수 있다.

> 위반 차단은 100%, 정상 문구 오차단은 0%, 대안은 100% 유효하다.
> 다만 검색 정밀도는 0.387이고 그건 top-k 고정의 대가이며,
> REG-033·REG-036 법률 조문 2개는 구조적으로 도달할 수 없고, 
> 한 문항(R-055 골든 데이터셋 문항)에서 판정은 평균적으로 5회 중 1회 흔들린다.

**같은 시스템인데 두 문장의 신뢰도가 다르다.** 그 차이를 만든 것이
골든 데이터셋 67문항과 3계층 지표, 그리고 조건을 고정한 재현 가능한 측정이다.

검증 함수를 만든 것보다 **검증 함수를 검증하는 방법을 만든 것**이
이 작업의 실제 결과물이라고 생각한다.
