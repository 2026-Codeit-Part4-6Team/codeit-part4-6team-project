# 1. Abstract

소상공인이 광고를 만들려면 상권과 검색 관심도를 해석하고, 실행할 전략을 고른 뒤, 채널에 맞는 문구와 이미지를 제작해야 한다. 완성된 광고가 과장 표현이나 법률 위반을 포함하지 않는지도 확인해야 한다. 그러나 이 과정은 데이터 검색, 전략 수립, 콘텐츠 제작, 검수를 서로 다른 도구에서 반복해야 하며 전문 지식이 없는 사용자가 직접 수행하기 어렵다.

매출부스터는 이 과정을 하나의 사용자 흐름으로 연결한 소상공인 마케팅 AI 플랫폼이다. 컨설턴트 챗봇은 가게 정보와 상권·검색 데이터를 바탕으로 실행 가능한 전략을 제안한다. 기본 챗봇은 선택한 플랫폼에 맞춰 광고 카피와 이미지를 3안씩 생성한다. 공용 검증 계층은 입력, 광고 규제, 출력, 응답 완결성을 검사한다. 서비스 계층은 인증, 가게 정보, 무료 사용량과 유료 크레딧(Credit), 결과 승인, 생성 이력, 두 챗봇 간 연계를 담당한다.

모델의 자연어 품질과 시스템 안정성을 같은 점수로 합치지 않고 각 평가의 목적에 맞게 분리했다. 기본 챗봇은 57개 유효 문항에서 최종 채택안의 LLM Judge 평균 4.72점을 기록했고, X-배너 가독성은 4.13점에서 4.60점으로 개선됐다. 컨설턴트 챗봇은 60문항에서 실패율 0%, 계약 준수율과 트렌드 경로 일치율 100%, LLM Judge 평균 4.325점을 기록했다. 공용 검증 계층은 67문항에서 위반 차단률 100%, 과잉 차단률 0%, 대안 유효성 100%를 기록했지만 RAGAS 종합 점수는 목표 0.70에 못 미치는 0.6545였다. 서비스 E2E에서는 회원가입부터 생성·결과·이력까지의 정상 흐름을 확인했으며, 일부 오류 주입과 새로고침 복구 경로는 미확정 과제로 남았다.

외부 API 일부가 실패하면 남은 데이터로 응답했고, 필드·호출 경로는 코드로 검사했으며, 성능이 나빠진 변경은 롤백했다. 최종 시스템은 전략 수립, 광고 생성, 검증, 저장과 재사용을 하나의 서비스 흐름으로 연결한다.

**주요어** LangGraph, 생성형 AI, 소상공인 마케팅, Cache-Aside, RAG, LLM Judge, E2E

# 2. Introduction

## 2.1 배경과 문제 정의

소상공인의 마케팅 질문은 짧지만 답변에 필요한 조건은 복합적이다. “이번 달에 어떤 행사를 하면 좋을까요?”라는 질문에도 업종, 위치, 주변 경쟁점, 홍보할 상품, 시점, 채널이 함께 고려돼야 한다. 범용 LLM은 빠르게 아이디어를 제시할 수 있지만 해당 가게의 상권을 자동으로 알지 못한다. 반대로 공공 API의 원시 수치만 제공하면 사용자가 그 수치를 어떤 행동으로 바꿔야 하는지 판단하기 어렵다.

광고 제작 단계에도 별도의 문제가 있다. 짧은 광고 문구는 채널별 길이와 표현 방식이 다르고, 이미지 안의 제품과 문구가 서로 어울려야 한다. 생성형 모델은 금지 지시가 있어도 “최고”, “완벽한” 같은 표현을 다시 만들 수 있다. 따라서 생성 프롬프트만 조정하는 방식으로는 품질과 안전성을 동시에 보장하기 어렵다.

서비스 관점에서는 모델이 잘 동작하는 것만으로 충분하지 않다. 사용자의 가게 정보, 사용량, Credit, 생성 상태와 이력이 일관되게 저장돼야 하며, 컨설팅 결과를 광고 생성으로 넘길 때 원본 소유권도 확인해야 한다. 외부 API나 이미지 생성 중 일부가 실패했을 때 비용을 복구하고 사용자가 다음 행동을 알 수 있도록 안내하는 흐름도 필요하다.

| AS-IS | 발생하는 문제 | TO-BE |
| --- | --- | --- |
| 검색·분석·제작·검수를 각각 수행 | 시간과 전문 지식이 필요함 | 한 서비스에서 전략부터 광고까지 연결 |
| 범용 LLM의 일반적인 조언 | 실제 상권과 가게 조건이 부족함 | 실측 상권·트렌드 데이터를 선택적으로 제공 |
| 프롬프트만으로 금지 표현 예방 | 지시를 우회하거나 다시 생성함 | 생성 전후의 검증 계층을 별도로 배치 |
| 모델 결과만 반환 | 과금·이력·승인·재사용이 끊김 | 서비스 계층이 요청과 결과의 생명주기를 관리 |

## 2.2 목표와 요구사항

매출부스터의 목표는 “광고를 만들어 주는 챗봇” 하나를 구현하는 것이 아니다. 상권 근거를 전략으로 바꾸고, 전략을 광고 결과로 변환하며, 결과를 검증하고 서비스에서 다시 사용할 수 있게 하는 것이 목표다.

이를 네 가지 질문으로 구체화했다.

1. 질문에 필요한 외부 데이터만 조회하면서 일부 조회 실패를 허용할 수 있는가.
2. 플랫폼에 맞는 카피와 이미지를 3안으로 생성하고 결과 계약을 유지할 수 있는가.
3. 생성형 모델이 만든 위험 표현을 사후 검증하고 사용할 수 있는 대안까지 제공할 수 있는가.
4. 인증, 과금, 생성 상태, 결과 승인과 이력을 실제 사용자 여정으로 연결할 수 있는가.

| 영역 | 필수 요구사항 | 검증 기준 |
| --- | --- | --- |
| 컨설팅 | 상권·트렌드·계절성을 질문에 맞게 사용 | 실패율, 계약 준수율, 트렌드 경로 일치율 |
| 광고 생성 | 채널별 카피·이미지 3안 생성 | 계약 준수, LLM Judge, 이미지 rubric, CLIP |
| 안전성 | 입력·규제·출력·완결성 검사 | 위반 차단, 과잉 차단, 대안 유효성, 표현 불변성 |
| 서비스 | 인증부터 결과·이력까지 상태 유지 | 화면·API·DB를 연결한 E2E 관찰 |
| 운영 | 외부 API 호출과 생성 비용 관리 | Cache-Aside, Credit 예약·복구, 평가 사전 승인 |

## 2.3 프로젝트 범위

컨설턴트 챗봇은 전략을 만들고 기본 챗봇은 광고 카피와 이미지를 만든다. 컨설턴트가 기본 챗봇을 직접 호출하지는 않는다. 사용자가 “이 전략으로 광고 만들기”를 선택하면 서비스가 저장된 컨설팅 결과의 소유권과 상태를 확인한 뒤 `source_context`로 조립해 기본 챗봇에 전달한다.

공용 규제 검증도 광고가 생성되는 기본 챗봇에만 적용한다. 컨설턴트에는 입력 검사, 출력 검사, 응답 자체 검사 3종을 연결했고, 근거 없는 최상급 표현과 질병 효능 표현은 전략 프롬프트에서 예방한다. 컨설턴트의 `strategy_check`는 현재 빈 딕셔너리를 반환하는 예약 스텁이며 구현 완료 기능으로 계산하지 않는다.

## 3.1 기존 접근의 장점과 한계

| 접근 | 장점 | 이 프로젝트에서 확인한 한계 |
| --- | --- | --- |
| 범용 LLM 단독 생성 | 빠르게 자연어 결과를 만듦 | 상권 근거, 산술, 금지 표현을 일관되게 통제하기 어려움 |
| 외부 API 결과 직접 제공 | 실제 수치와 출처를 확보함 | 원시 수치를 실행 가능한 전략으로 바꾸지 못함 |
| 키워드 금칙어 필터 | 빠르고 비용이 들지 않음 | 문맥을 구분하지 못해 정상 표현을 막을 수 있음 |

| 순차 파이프라인 | 구현과 추적이 단순함 | 독립적인 외부 조회가 누적돼 대기 시간이 늘어남 |

## 3.2 프로젝트의 접근

매출부스터는 한 방법에 모든 판단을 맡기지 않았다. 상태와 분기가 필요한 작업은 LangGraph 노드로 분리하고[1], 확정 가능한 계약은 Python 규칙으로 검사했다. 의미 해석이 필요한 품질 평가는 LLM Judge에 맡겼다[3]. 외부 데이터는 Cache-Aside로 재사용하되 캐시 장애가 원본 API 호출까지 막지 않게 했다[2]. 법률 규제는 키워드 스크리닝 뒤 벡터 검색과 LLM 판정을 수행하는 2단 구조로 설계했다.

판단 책임은 계층별로 제한했다. 트렌드 검색 대상이 없는 질문에는 API를 호출하지 않는다. 계절성은 외부 출처가 아니라 날짜 계산 결과이므로 `sources`에 넣지 않는다. 할인율 계산이나 지역 특성처럼 검증할 데이터가 없는 사실을 프롬프트가 임의로 확정하지 않게 한다.

## 3.3 평가 방법의 분리

자유 형식 결과를 한 점수로만 평가하면 실패 유형이 가려진다. 따라서 필드 누락, 배열 길이, 허용되지 않은 숫자, 호출 경로는 규칙으로 확인했다. 근거 충실도, 실행 가능성, 구체성, 자연스러움은 LLM Judge가 평가했다[3]. 이미지 정합성은 CLIP과 비전 rubric으로 확인했고, 법률 RAG는 RAGAS를 포함한 분류·검색·견고성 지표를 나눠 측정했다[4].

# 4. Method

## 4.1 서비스와 사용자 여정

사용자는 회원가입 과정에서 업종과 주소를 등록한다. 서비스는 주소를 좌표로 변환해 저장하고 대시보드에서 기본 챗봇과 컨설턴트 챗봇 중 하나를 선택하게 한다. 생성 전에 무료 사용량 또는 예상 Credit 차감을 보여주고 동의를 받은 뒤 요청을 실행한다.

컨설턴트 경로에서는 전략 요약, 실행 항목, 근거, 출처와 추천 질문을 제공한다. 사용자는 후속 질문을 이어가거나 전략을 기본 챗봇 입력으로 넘길 수 있다. 기본 챗봇 경로에서는 Instagram 또는 X-배너를 선택하고 광고 카피와 이미지 3안을 생성한다. 사용자가 결과를 승인하면 선택한 결과만 게시 상태로 전환하며, 생성 이력은 마이페이지에서 다시 조회할 수 있다.

![사용자 여정](<../assets/02_user_journey.png>)

*그림 1. 회원가입과 가게 등록부터 컨설팅, 광고 생성, 승인과 이력 조회까지의 사용자 여정.*

| 단계 | 사용자 행동 | 시스템 처리 |
| --- | --- | --- |
| 1 | 회원가입과 가게 등록 | 인증, 지오코딩, 가게 정보 저장 |
| 2 | 챗봇 선택 | Basic 또는 Consultant 요청 준비 |
| 3 | 질문과 옵션 입력 | Estimate, 무료 사용량·Credit 확인 |
| 4 | 생성 동의 | Credit 예약, 생성 상태 전이 |
| 5 | 결과 확인 | 전략 또는 카피·이미지 표시 |
| 6 | 승인·연계·재사용 | 게시 상태, source_context, 생성 이력 저장 |

서비스는 공개 요청과 내부 모델 입력을 구분한다. 사용자는 `source_gen_id`를 전달하지만 가게 정보와 `source_context`는 서버가 DB에서 조립한다. 이 경계로 다른 사용자의 결과를 임의로 참조하는 것을 막고, 프론트엔드가 모델 내부 형식을 알 필요도 없게 했다.

## 4.2 전체 시스템 아키텍처

![전체 시스템 아키텍처](<../assets/01_system_architecture.png>)

*그림 2. Frontend, Service, Basic·Consultant 모델, 검증 계층, 저장소와 외부 API의 연결 구조.*

사용자의 요청은 React/Vite 화면에서 FastAPI로 전달된다. 서비스는 인증, Estimate, 생성 요청, 결제와 이력을 처리하고 Basic 또는 Consultant 모델을 호출한다. 모델은 공용 요청·응답 계약을 사용하며, 외부 데이터와 검증 함수는 각 노드에서 필요한 시점에 호출된다. 결과는 SQLite에 저장되고 화면의 결과 카드와 마이페이지 이력으로 반환된다.

| 계층 | 기술 | 선택 이유 |
| --- | --- | --- |
| Frontend | React, Vite | 상태 기반 화면과 반응형 사용자 흐름 구현 |
| Backend | FastAPI | 명시적인 REST API와 모델 호출 경계 구성 |
| 모델 오케스트레이션 | Python, LangGraph | 분기·병렬 실행·재시도·종료 조건 표현 |
| 데이터 | SQLite, SQLAlchemy | 로컬·시연 환경에서 동일한 저장 계약 유지 |
| 생성 모델 | OpenAI API, gpt-image-2 | 구조화 자연어와 광고 이미지 생성 |
| 외부 데이터 | 소상공인시장진흥공단, NAVER API, NAVER Maps | 상권·검색 관심도·위치 정보 확보[5][6][7] |
| 검증 검색 | 임베딩, NumPy 코사인 유사도 | 법률 KB에서 관련 근거 검색 |
| 운영 | Docker Compose, GitHub Actions, GCP VM | 실행 환경 표준화와 배포 자동화 |

배포 파이프라인은 Python 테스트와 Ruff, Compose 해석과 배포 스크립트 점검, Backend·Frontend 기동과 healthcheck를 단계별로 확인한다. 실제 배포는 이미지 빌드·push 후 GCP VM에서 서비스를 기동하는 구조다. 최종 보고서에서는 구현된 CI 구조와 실제 CD 실행 증적을 구분하며, 확인되지 않은 배포 성공률은 제시하지 않는다.

## 4.3 서비스 계층의 상태와 과금

생성 요청은 `pending → generating → done` 또는 `failed` 상태로 이동한다. 서비스는 모델 호출 전에 무료 사용량 또는 Credit을 예약하고, 성공하면 확정하며, 실패하면 정책에 따라 복구한다. 모델 호출 중에는 긴 DB write transaction을 유지하지 않도록 상태 저장과 외부 호출의 경계를 분리했다.

Idempotency-Key와 요청 해시는 네트워크 재전송으로 같은 요청이 중복 처리되는 것을 막는다. 다만 사용자가 화면에서 의도적으로 “다시 만들기”를 누르는 동작은 새 요청이므로 멱등 재시도와 같은 정책으로 취급하지 않는다. E2E에서 재실행 시 사용량 차감이 관찰된 이유도 이 두 상황이 분리되지 않은 데 있다.

## 4.4 기본 챗봇

기본 챗봇은 사용자의 질문과 플랫폼을 입력받아 서로 다른 광고 카피 3안과 대응 이미지 3장을 만든다. 전체 파이프라인은 입력, 컨텍스트 준비, 생성·검증, 출력의 네 구간으로 구성된다.

![기본 챗봇 파이프라인](<../assets/03_basic_pipeline.png>)

*그림 4. 입력, 컨텍스트 준비, 광고 생성, 출력 조립·검증으로 구분한 기본 챗봇 파이프라인.*

1. 입력 보안 검사와 질문 분석을 거쳐 정보가 부족하면 재질문으로 종료한다.
2. 플랫폼을 확정한 뒤 상권, 트렌드, 벤치마크, 계절성 정보를 준비한다.
3. 카피 생성, 랭킹, 규제 검사, 이미지 생성과 이미지 검수를 수행한다.
4. 채널 형식으로 결과를 조립하고 출력 보안 검사와 self-check를 수행한다.

카피 생성 모델은 초기 Groq `llama-3.3-70b-versatile`에서 다국어 문자가 섞이고 사전 입력을 무시하는 문제가 확인돼 OpenAI 계열로 교체했다. 이미지 생성은 `gpt-image-1`의 한글 깨짐을 피하기 위해 텍스트 제거와 PIL 합성을 실험했지만 문구 잘림이 발생했다. 최종적으로 `gpt-image-2`를 사용해 이미지 안의 텍스트를 생성하는 방식으로 정리했다.

이미지 정합성 평가에서는 영어 중심 CLIP 모델에 한국어 카피를 직접 넣을 때 정답과 오답의 차이가 작았다. 5개 업종·채널 쌍에서 정답-오답 평균 차이는 한국어 0.0494, 영문 캡션 0.1283이었다. 이에 따라 이미지 생성용 프롬프트와 별도로 CLIP 채점용 영문 캡션을 만들었다. 이 실험은 방향성을 확인한 것이며 번역의 반복 일관성과 통계적 유의성을 보장하는 결과는 아니다.

![기본 챗봇 광고 결과 3안](<../images/basic_3_proposals.png>)

*그림 5. 기본 챗봇이 한 요청에 대해 생성한 광고 카피와 이미지 3안.*

## 4.5 컨설턴트 챗봇

컨설턴트 챗봇은 질문을 분석한 뒤 추천 질문, 상권, 트렌드, 계절성 네 작업을 병렬로 준비한다. 네 결과가 모이면 전략을 만들고 출력 보안 검사와 self-check를 수행한다.

![컨설턴트 챗봇 파이프라인](<../assets/04_consultant_pipeline.png>)

*그림 6. 추천 질문·상권·트렌드·계절성의 4-way 병렬 처리와 전략 생성·검증 경로.*

트렌드는 질문에 구체 상품이나 메뉴가 있을 때만 조회한다. “아이스라테 신메뉴 홍보 전략”은 `아이스라테`를 키워드로 사용하지만 “매출을 늘리려면?”은 검색 대상을 특정하지 않으므로 API를 호출하지 않는다. 검색 대상이 없는 상태에서 임의 키워드를 붙이면 질문과 무관한 데이터가 근거처럼 사용될 수 있기 때문이다.

상권 데이터는 반경 내 전체 매장 수, 동일 업종 매장 수, 가장 가까운 동일 업종 거리, 업종 분포로 제한한다. 좌표를 소수 셋째 자리로 반올림한 키로 7일간 캐시한다. 트렌드도 7일 Cache-Aside를 적용하고 최근 30일을 전반과 후반으로 나눠 검색 관심 방향을 계산한다. API 키가 없거나 조회가 실패하면 `None`을 반환하며 남은 데이터로 상담을 계속한다.

날씨 API는 최종 범위에서 제거했다. 대신 KST 기준 날짜에서 계절과 월 상·중·하순을 계산한다. 평가에서는 기준일을 고정해 재현성을 확보한다. 계절성은 외부 데이터가 아니므로 출처에 넣지 않으며, 날짜만으로 수요 증가를 단정하지 않는다.

최종 응답은 제목, 요약, 실행 항목 1~3개, 근거, 외부 데이터 출처, 추천 질문 3개로 구성된다. 추천 질문은 사용자가 챗봇에 이어서 물어보는 방향이어야 한다. 프롬프트 수정 뒤 10문항의 30개 칩을 직접 확인해 화자 방향 오류가 없는지 점검했다.

| --- | --- |
| ![컨설팅 결과와 광고 연계 버튼](<../images/link_to_ads.png>) | ![연계 후 광고 결과 3안](<../images/generate_result_from_strategy.png>) |

## 4.6 공용 검증 계층

검증 함수는 생성형 모델이 사용자에게 결과를 보여주기 전 네 지점에서 동작한다.

| 함수 | 역할 | Basic | Consultant |
| --- | --- | ---: | ---: |
| `check_input` | 인젝션·불법 요청 검사 | 적용 | 적용 |
| `check_regulation` | 광고법·식품광고법 위반 검사 | 적용 | 미적용 |
| `check_output` | 개인정보·민감정보 노출 검사 | 적용 | 적용 |
| `self_check` | 근거와 응답 완결성 검사 | 적용 | 적용 |

컨설턴트가 규제 검사를 사용하지 않는 이유는 출력이 광고 카피가 아니라 전략이기 때문이다. 컨설팅 결과가 광고가 되는 시점에는 기본 챗봇의 규제 노드를 통과한다.

`check_regulation`은 2단 구조다. 먼저 키워드 스크리닝으로 명백한 위반을 비용 없이 차단한다. 문맥 판단이 필요한 경우 표시·광고 관련 법률[8]을 정리한 36개 KB 청크에서 관련 조문 3개를 검색하고 `gpt-5.4-mini`가 검색된 조문만 근거로 판정한다. 위반 결과에는 대안 문구를 만들고 그 대안을 다시 검사한다.

![공용 검증 계층](<../assets/05_validation_pipeline.png>)

*그림 8. 공용 검증 함수의 적용 위치와 광고 규제 검사의 2단 판정 구조.*

법률 검색을 사용하는 목적은 차단률 자체가 아니다. 같은 날짜와 같은 67문항에서 1단만 사용해도 위반 차단률은 100%였지만 대안 유효성은 90.3%였다. 2단 RAG를 사용하면 대안 유효성이 100%가 되고 과잉 차단률도 8.33%에서 0%로 줄었다. 반면 P95 지연은 0.016초에서 1.312초로 늘고 204,556토큰이 사용됐다. 이 비용은 “안 된다”에서 끝내지 않고 사용할 수 있는 대안을 제시하기 위한 선택이다.

## 4.8 협업 방식

## 5.3 재현성 통제

Consultant와 Validation은 fixture와 데이터셋 버전을 기록했다. Judge는 생성 모델과 분리하고 temperature를 0으로 설정했다. 다만 temperature 0도 완전 결정론을 보장하지 않으므로 작은 차이는 반복 측정과 앵커 문항으로 해석해야 한다. Basic Judge는 고정 응답 5건을 3회 채점했을 때 60문항 환산 표준편차 0.0072로 기준 0.05 이하를 확인했다.

### 서비스 E2E

1차 로컬 Docker Compose와 2차 GCP Demo에서 회원가입, 지오코딩, 대시보드, 광고 생성, 결과 3안, 사용량 반영, 생성 이력의 정상 흐름을 확인했다. 컨설턴트의 전략과 추천 질문도 표시됐다. 2차에는 불법 품목 차단, 재질문, Provider 장애 시 Credit 미소모, 일부 proposal 실패 후 나머지 결과 표시가 확인됐다.

남은 문제도 있었다. Credit 부족 화면에는 충전 CTA가 없었고, 새로고침 뒤 진행 중 요청의 복구 안내가 확인되지 않았다. 같은 입력을 사용자가 다시 제출하면 사용량이 다시 차감됐으며, 이는 네트워크 재시도와 사용자의 재생성 동작을 UI에서 구분해야 하는 문제다. Trend API만 실패시키는 독립 경로와 일부 Consultant→Basic 연계는 해당 회차에서 실행하지 못해 Blocked로 기록했다.

## 7.2 공통적으로 얻은 판단

첫째, 프롬프트 규칙을 늘리는 것이 항상 품질 향상으로 이어지지는 않았다. Basic 7차는 금지 표현을 늘렸지만 점수가 하락했고, Consultant의 36문항 실험은 실행 항목의 우회를 막지 못했다. 지시를 추가하기 전에 실패를 재현하고, 효과가 없으면 롤백하는 절차가 필요했다.

둘째, 정확한 계약과 계산은 생성 모델 밖에 두는 편이 안전했다. 필드 수, 허용 숫자, 호출 경로, 소유권, 사용량은 코드와 DB가 판정해야 한다. LLM은 전략과 표현을 만들되 확정할 근거가 없는 지역 특성이나 산술을 임의로 결정하지 않게 해야 한다.

셋째, 실패와 미측정을 구분해야 했다. 실행해서 기대와 달랐던 Fail과 선행조건이 없어 실행하지 못한 Blocked를 합치면 개선 우선순위를 잘못 판단할 수 있다. 서비스 E2E 결과는 이 구분을 유지했다.

# 8. Conclusion

매출부스터는 컨설팅, 광고 생성, 안전성 검증, 서비스 운영을 하나의 사용자 흐름으로 연결했다. 컨설턴트는 필요한 데이터만 조회해 전략을 만들고, 기본 챗봇은 채널별 광고 3안을 생성한다. 검증 계층은 생성 전후의 위험을 검사하고, 서비스는 인증·과금·상태·승인·이력을 관리한다. 각 파트는 공개 계약을 기준으로 연결돼 내부 구현이 달라도 같은 요청과 결과 형식을 유지한다.

정량 결과만 보면 모든 목표를 달성한 프로젝트는 아니다. Basic은 텍스트 구체성과 X-배너 가독성이 개선됐지만 응답시간과 이미지 텍스트 통제 문제가 남았다. Consultant는 실패율과 계약·경로 지표를 안정화했지만 업종과 지역 범위가 제한적이고 비수치 과잉 추론을 운영 중에 검사하지 못한다. 검증 계층은 차단과 대안 품질 목표를 달성했지만 RAGAS 종합 점수는 목표에 미달했다. 서비스는 정상 여정을 연결했지만 새로고침 복구와 일부 장애 주입 경로는 미확정이다.

생성형 AI의 품질은 프롬프트 하나로 통제되지 않았다. 자연어 생성, 계약 검사, 데이터 조회, 법률 근거, 과금과 상태 관리를 서로 다른 계층에 두자 실패 원인이 분리됐다. 점수가 오르지 않거나 회귀를 만든 실험은 롤백해 최종 기준선에서 제외했다.

후속 우선순위는 네 가지다.

1. 이미지 안의 텍스트를 OCR로 추출해 광고 규제 검증 범위에 포함한다.
2. 이미지 3장 생성은 비동기 작업 큐나 별도 추론 워커로 분리한다.
3. Consultant의 사용자 명시 시점을 구조화해 기본 계절성 노드의 실행 여부를 결정한다.
4. 새로고침 복구, Credit 부족 CTA, Trend 단독 장애를 재현 가능한 E2E fixture로 고정한다.

기능의 개수보다 비교 가능한 조건과 폐기 기준이 결과 해석에 더 직접적으로 기여했다. 후속 개발에서도 데이터셋과 평가 조건을 먼저 고정하고, 작은 파일럿에서 실패 유형을 확인한 뒤 전체 평가와 배포 검증으로 확장해야 한다.

# 9. Retrospective

## 9.1 전민재

**기술적인 성장**

표시광고법·식품표시광고법 조문 36개로 지식베이스를 구축하고, 키워드 스크리닝과 벡터 검색·LLM 판정을 결합한 2단 검증 파이프라인을 설계·구현했다. 골든 데이터셋 67문항과 분류·검색·견고성 3계층 평가 체계를 직접 설계해, "잘 되는 것 같다"가 아니라 위반 차단률 100%, 과잉 차단률 0%처럼 숫자로 답할 수 있는 수준까지 검증 방법론을 완성했다.


**협업 측면**

PM으로서 마일스톤을 미리 설계해 팀 프로젝트가 예상 일정대로 순차적으로 진행되도록 관리했다. 컨설턴트 챗봇에는 법률 규제 검증 기능을 붙이지 않기로 한 판단처럼, 각 검증 함수를 어느 챗봇에 연결할지에 대한 근거를 문서로 정리해 두어 발표나 리뷰에서 나올 질문에 미리 대응할 수 있었다.

**아쉬운 점**

PR 리뷰 처리가 예상보다 시간이 더 걸려 스프린트마다 반복적으로 지연됐다. 또한 RAGAS-SCORE 종합 평가 지표가 목표(0.70)에 못 미쳤는데, top-k를 고정한 구조에서 context_precision의 상한이 애초에 낮았다는 점을 목표 설정 단계에서 미리 파악하지 못한 점이 아쉬웠다.

**향후 적용**

다음 스프린트부터는 PR 리뷰를 체계적인 순서로 처리해 지연을 줄이고, 지표 목표치를 세우기 전에 구조적 상한부터 계산해 현실적인 목표를 설정하겠다. 이미지 안의 텍스트 검증처럼 범위 밖으로 남겨둔 영역도 다음 단계에 포함하겠다.

## 9.2 윤승준

**기술적인 성장**

LangGraph의 상태와 조건부 엣지를 기반으로 데이터 조회, 전략 생성, 검증으로 이어지는 파이프라인을 통합하고, Consultant 결과를 source_gen_id와 source_context로 Basic 광고 생성까지 연결하는 과정을 경험했다. 또한 상권·검색 트렌드 API의 Cache-Aside와 부분 성공 정책을 적용하며 외부 서비스 장애에 대응하는 방법을 익혔다.

Docker Compose와 GCP 환경의 설정, 모델 사전 로딩, CI/CD 배포 흐름을 점검했고, 실제 배포 환경에서 발생하는 환경 변수·캐시·포트·세션 문제를 추적했다. 골든 데이터셋과 E2E 시나리오를 활용해 화면부터 서비스·모델·DB까지 연결되는 흐름을 검증하는 경험도 얻었다.

**협업 측면**

담당 범위와 API 계약, 상태 구조, 브랜치 의존성을 문서로 정리한 덕분에 여러 담당자의 작업을 통합할 때 충돌 원인과 영향 범위를 비교적 빠르게 파악할 수 있었다. 특히 기준 브랜치를 맞추지 않아 기존 기능이 되돌아가는 문제를 경험하며, PR 순서와 기준 커밋을 명확히 관리하는 것이 중요하다는 점을 배웠다.

**아쉬운 점**

일부 프롬프트와 모델 출력은 예상과 다르게 동작해 E2E 테스트에서 재현과 원인 추적에 시간이 많이 필요했다. Basic 챗봇의 이미지 생성처럼 외부 모델 호출이 연속되는 기능은 응답 시간이 길어지는 한계도 확인했다. 또한 브랜치 통합과 배포 환경 설정에 필요한 시간을 초기에 충분히 예상하지 못해 후반 작업이 집중된 점이 아쉬웠다.

**향후 적용**

다음 프로젝트에서는 구현 전에 API 계약, 환경 변수, 브랜치 의존성, 평가 기준을 먼저 확정하고 통합 테스트 시간을 일정에 별도로 반영할 것이다. 기술적으로는 날짜 계산·계약 검증·사용량 정산처럼 정답이 명확한 영역은 코드로 처리하고, 장시간 모델 추론은 비동기 처리나 별도 추론 서버를 검토해 사용자 대기 시간을 줄일 것이다.

## 9.3 김재헌

**기술적인 성장**

LangGraph의 상태와 조건부 엣지를 활용해 데이터 조회, 전략 생성, 검증으로 이어지는 파이프라인과 병렬 처리 구조를 구현했다. 상권·검색 트렌드 Open API를 연동하고 Cache-Aside와 부분 성공 정책을 적용하면서 외부 서비스 장애에 대응하는 방법도 배웠다. 또한 골든 데이터셋과 규칙 기반 검사, LLM Judge로 변경 효과를 측정하며 생성형 AI를 평가하고 개선하는 과정을 경험했다.

**협업 측면**

개발 전에 담당 범위와 API 계약, 인터페이스를 설계 문서로 정리한 덕분에 여러 담당자가 동시에 작업하면서도 데이터 형식이나 책임 범위로 인한 충돌을 줄일 수 있었다. 변경이 필요할 때도 문서를 기준으로 영향 범위를 확인하며 조율할 수 있었다.

**아쉬운 점**

일부 프롬프트 개선안이 실제 응답에서는 예상과 다르게 작동해 롤백과 재검증을 반복했다. 또한 평가와 수정에 필요한 시간을 초기에 충분히 반영하지 못해 후반부에 작업이 집중된 점이 아쉬웠다.

**향후 적용**

이후 프로젝트에서는 담당 범위와 API 계약, 인터페이스, 평가 기준을 포함한 설계 문서를 먼저 확정하되, 설계 단계가 길어지지 않도록 완료 기한을 명확히 정할 것이다. 기술적으로는 계산과 계약 검증처럼 정답이 명확한 영역을 코드로 처리하고, LLM은 자연어 생성과 해석에 집중하도록 역할을 분리할 것이다.

## 9.4 조희원

**기술적인 성장**

LangGraph 기반 15개 노드로 구성된 파이프라인을 설계하고, 노드 단위 테스트·통합 테스트·계약 테스트로 기능적 정확성을 검증했다. 카피 생성 모델과 이미지 생성 모델 선정 과정에서 다국어 오염, 한글 텍스트 깨짐 같은 문제를 실측으로 확인하고 반복 검증을 통해 해결했다. 또한 LLM Judge 채점의 재현성과 CLIP Score의 언어별 판별력을 본 평가 전에 별도로 검증해, 이후 프롬프트 튜닝 결과를 신뢰성 있게 비교할 수 있는 기반을 마련했다. 이를 바탕으로 텍스트 카피 프롬프트를 8라운드, 이미지·배너 프롬프트를 10라운드에 걸쳐 반복 튜닝하며 정량 지표 기반으로 개선 여부를 판단하는 과정을 경험했다.


**협업 측면**

초반에 담당 범위와 API 계약, 인터페이스를 기획 문서로 체계적으로 정리해둔 덕분에 담당자 간 합의가 빠르게 이루어졌고, 나중에 각자 작업한 내용을 합칠 때도 데이터 형식이나 책임 범위 충돌 없이 매끄럽게 통합할 수 있었다. 의존 함수를 목업으로 먼저 커밋해 인터페이스 계약을 고정하는 팀 원칙도 따라, 컨설턴트 챗봇의 전략·근거를 기본 챗봇 카피 생성과 연계하는 작업 역시 충돌 없이 진행할 수 있었다.


**아쉬운 점**

프롬프트 텍스트 지시만으로는 생성 모델의 특정 행동을 안정적으로 통제하기 어렵다는 한계를 텍스트·이미지 두 트랙에서 반복 확인했다. 텍스트 카피의 과장 표현 문제는 금지 예시를 늘려도 재발해 뚜렷한 해결책을 찾지 못한 채 백로그로 남겼고, 위치 정보 활용 규정의 근본적인 재설계도 이번 세션에서는 다루지 못했다. 이미지 쪽에서도 하단 정보란 자리 채우기, 상단 시간·날짜 노출 문제는 여러 라운드에 걸쳐 시도했지만 끝내 완전히 해결하지 못한 점들이 아쉽다.


**향후 적용**

이미지 세부사항 반영 단계에서는 특정 단어가 포함된 문장을 텍스트 지시 대신 코드에서 미리 분리해 처리하는 방식으로 일부 문제를 해결했다. 향후 이런 코드 레벨 분리를 텍스트 카피 쪽에도 더 적극적으로 적용해, 프롬프트 지시에만 의존하는 영역을 줄일 것이다. 아울러 튜닝 초기 단계부터 정답이 명확한 규칙과 LLM 판단이 필요한 영역을 구분해 설계할 것이다.
