## 1) Abstract - 초록

본 보고서는 소상공인 광고·상권 컨설팅 서비스의 서비스 계층을 대상으로 프론트엔드, 백엔드, 모델 그래프, 데이터베이스, 외부 API, Docker Compose 및 GCP 배포 경계를 검증한 결과를 정리한다. 검증은 화면의 성공 여부만 세지 않고,

> **화면 → Frontend 상태/API → Backend 라우터·서비스 → 모델 그래프·노드 → DB/외부 API**

순서로 요청과 응답의 계약을 추적하는 방식으로 수행했다.

Service 구현의 핵심 성과는 테스트 케이스 자체가 아니라, 계약을 기준으로 인증·지오코딩, 무료 사용량·Credit 예약/복구, 생성 오케스트레이션, 결과 직렬화, 실제 모델 런타임, React 화면, 생성 이력·결제·지도·배포 경계를 단계적으로 연결한 것이다. 아래 결과는 각 마일스톤의 구현 범위와 통합 실행 결과를 분리해 기록한다.

## 2) Introduction - 소개

### 2.1 서비스와 Service 담당 범위

대상 서비스는 두 챗봇을 하나의 웹서비스로 묶는다.

- Basic 챗봇: 사용자가 고른 플랫폼에 맞춰 광고 카피와 이미지를 생성한다.
- Consultant 챗봇: 상권·트렌드·계절성 정보를 바탕으로 전략을 제안한다.
- 연계 흐름: Consultant 전략의 `source_gen_id`를 Basic 생성 폼으로 전달한다.
- 공통 서비스: 로그인, 가게 정보, 일일 무료 사용량, Credit, Estimate 동의, 생성 상태, 결과 승인, 충전, 생성 이력을 관리한다.

Service 담당의 검증 대상은 모델 알고리즘 자체가 아니라 모델 호출 계약이 실제 사용자 흐름과 DB·과금·화면에 일관되게 연결되는지 여부다. 따라서 `platform`은 사용자가 선택한 값을 사용하고 Consultant 결과에서 자동 추론하지 않으며, 가게 정보와 `source_context`는 서버가 DB와 원본 생성 기록을 기준으로 구성하는 것을 전제로 한다.

### 2.2 검증 질문

본 보고서는 다음 질문에 답하도록 구성했다.

1. 광고 생성과 Consultant→Basic 연계의 정상 요청이 화면·API·DB에서 같은 의미로 끝나는가?
2. 무료 사용량·유료 Credit·Estimate 동의·생성 이력의 순서와 값이 계약에 맞는가?
3. 차단·재질문·외부 오류·부분 실패·재시도·새로고침 경계에서 사용자가 다음 행동을 알 수 있는가?
4. 로컬 Compose와 GCP VM 배포 경계가 CI/CD의 검증 단계와 일치하는가?
5. 회차별 결과를 동일한 분모와 증적으로 비교할 수 있는가?

### 2.3 판정 용어

| 용어 | 이 보고서의 의미 |
| --- | --- |
| Pass | 기록된 화면·API·DB 관찰이 기대 계약과 일치함 |
| Fail | 실행되었고 기대 계약과 다르게 관찰됨 |
| Blocked | 권한·장애 주입·필수 환경 등 선행조건이 없어 실행하지 못함 |
| N/A | 해당 챗봇 또는 계약의 대상이 아님 |
| 미측정 | 정량 측정 또는 회차별 증적이 기록되지 않음 |

## 3) Method - 시스템 설계와 구현

### 3.1 서비스 경계 설계

서비스 통합 경계는 다음과 같이 모델 계층과 분리했다.

```
Frontend
  → FastAPI 인증·Estimate·Generate·History·Payment API
  → Credit 예약/차감/rollback 및 생성 상태 관리
  → Basic 또는 Consultant 모델 호출 계약
  → SQLite 생성·사용량·결제·이력
  → Trend/상권 외부 API 또는 cache
```

Consultant에서 Basic으로 이동할 때 Frontend가 전달하는 공개 입력과 Service가 내부에서 조립하는 값은 구분한다. 공개 요청에는 질문, 플랫폼, 보조 입력, 원본 생성 식별자를 사용하고, 가게 정보와 내부 `source_context`는 서버 소유 데이터로 구성한다. 서버는 `source_gen_id`의 소유권을 확인한 뒤 ModelRequest에 전달한다.

### 3.2 마일스톤별 구현 계보

구현은 계약과 책임 경계를 먼저 고정한 뒤 서비스·모델·화면·배포를 단계적으로 연결하는 방식으로 진행했다. 단계가 올라갈수록 이전 계층의 계약을 유지하면서 사용자 흐름의 완결 범위를 넓혔다.

| 구분 | 구현한 내용 | 결과 및 의미 |
| --- | --- | --- |
| D1 서비스 기반 | 평면 FastAPI 구조, Router·Service·Client 분리, 서비스 DB 모델, Public DTO와 Model DTO 분리, Mock Client, 결과 직렬화 | 실제 모델·인증·과금은 제외하고 계약·저장 경계를 먼저 검증 |
| D2 인증·지오코딩 | username 정규화, bcrypt, Session(user_id만 저장), 회원가입·로그인·로그아웃·`/users/me`, NAVER Geocoding, 좌표 검증, 422/503 분리, 개발·demo fallback | 외부 Provider 오류가 불완전한 User를 남기지 않도록 rollback |
| D3 사용량·과금 | KST 자정 무료 사용량 리셋, Basic·Consultant 비용, 무료 우선 Credit 예약, Estimate, 402, 멱등 rollback | Estimate는 상태를 변경하지 않고 BillingService가 정책을 단일화 |
| D4 생성 오케스트레이션 | 인증된 `/generate`, Idempotency-Key·request hash, StoreContext·`source_gen_id` 검증, pending→generating→done/failed, Model 호출, 저장, settle·compensation, stale recovery | 모델 호출 중 DB write transaction을 유지하지 않고 commit 전·후 실패를 분리 |
| D5 React 기본 화면 | React Shell, 로그인·회원가입, Dashboard, Sidebar, `/users/me` 복원, Estimate/Generate API client 연결, 반응형 구조 | 화면은 API client만 사용하고 Credit·StoreContext를 재계산하지 않음 |
| D6 챗봇 입력 흐름 | Basic·Consultant chat-first 입력, 플랫폼 선택, extra 5필드, Estimate→Generate 승인, Basic 3안·Consultant 전략 카드, 후속 질의, route/state 초기화 | 실제 Provider 연결과 이력·결제 API는 후속 단계로 분리 |
| D7 실제 모델 경계 | `models`, `cache`, `validation`, `shared_data` 런타임 패키징, Actual Docker target, 외부 API 환경변수 전달, 180초 요청 예산, CI 경량화와 실제 런타임 분리 | Basic·Consultant 내부 그래프와 프롬프트는 모델 담당 구현을 호출 |
| D8 결과 승인 | 생성 결과 승인, 선택 결과만 게시 상태로 전이, 이미지 검증과 안전한 저장 경계, 실패 상태 안내 | 생성 완료와 게시 확정을 분리해 미승인 결과가 게시되지 않도록 함 |
| D9 이력·계정 | 생성 이력 목록·상세, 검색·페이지네이션, 최신순 정렬, 실패 reason 표시, 통계와 계정 화면 연결 | 이력 조회와 생성 실행을 분리해 과거 결과를 재현 가능하게 함 |
| D10 제품 UI 고도화 | 브랜드·마스코트 UI, 로그인·회원가입·Dashboard·MyPage 반응형 보완, 결과·대기 피드백, HTTP 환경용 요청 식별자 생성, 채널 호환 | 시연 UI의 상태·접근성·플랫폼 표현을 서비스 계약과 맞춤 |

### 3.3 Basic·Consultant 모델 구현과 Service 연결

Basic·Consultant의 모델 내부 그래프와 프롬프트는 모델 담당 영역이며, Service는 두 모델의 공통 요청·응답 계약을 호출하고 결과를 화면·DB·과금 흐름으로 연결했다.

| 영역 | 통합된 모델 기능 | Service가 연결한 경계 |
| --- | --- | --- |
| Basic | 플랫폼별 광고 카피·이미지 생성, `extra` 입력 반영, 3안 결과, 입력·규제·출력·자체 검증 | 플랫폼·보조 입력을 ModelRequest로 전달하고 결과의 `status`, 카피·이미지, 사용량을 결과 카드와 생성 이력에 연결 |
| Consultant | 상권·Trend·계절성 기반 전략, `summary`·`actions`·`reasons`·`sources`, 추천 질문 칩 | 전략 응답을 채팅 화면에 표시하고 후속 광고 생성에 `source_gen_id`와 `source_context`를 전달 |
| 공통 계약 | ModelRequest/ModelResult 스키마, 기준일 주입, 검증 reason·message, 실패 상태 | 인증·Credit 예약, 생성 상태 전이, DB 저장, 오류 안내와 모델 결과의 변환·검증을 담당 |

### 3.8 후속 서비스 기능 구현

마일스톤 이후에는 발표·운영 흐름에 필요한 기능을 보강하였다.

| 구분 | 구현한 내용 | 결과 및 의미 |
| --- | --- | --- |
| 결과 승인·게시 | 승인 후 선택 결과만 게시 상태로 전이하고, 이미지 전체 원문은 저장하지 않도록 검증 | 생성 결과와 실제 게시를 분리하고 저장량·노출 위험을 줄임 |
| 생성 이력 | 검색·페이지네이션, 최신순 및 동일 시각 tie-breaker 정렬, 상세 조회, 실패 reason 안전 표시 | 생성 결과를 다시 찾고 실패 원인을 이해할 수 있음 |
| 결제 시연 | 서버 카탈로그, 멱등 구매, demo 전용 Credit 충전, PG 연동 전임을 화면·응답에 표시 | 실제 결제 없이 시연·과금 흐름을 검증할 수 있음 |
| Consultant→Basic 연계 | 전략에서 Basic 폼으로 이동하고 `source_gen_id`를 전달하며 서버가 원본 소유권·상태·schema를 재검증 | 전략 결과를 광고 생성으로 이어서 추적 가능 |
| X-배너 | `xbanner` wire 값, 채널별 레이아웃·합성 이미지, 기존 `banner` 이력 호환 | Instagram과 X-배너 결과를 구분하고 과거 이력을 안전하게 표시 |
| 규제·오류 안내 | `status`, `reason`, `message`를 결과 화면에서 구분하고 실패 안내를 노출 | 성공 카드와 차단·오류 카드를 혼동하지 않음 |
| 대기 화면 | 서버 대기 문구와 예시를 표시하고 로딩 스피너를 유지 | 장시간 생성 중에도 현재 상태와 다음 결과를 안내 |
| 지도·가게 정보 | 회원가입·가게 프로필에 주소 지오코딩과 Naver Maps 기반 지도 미리보기 연결 | 입력한 주소와 상권 기준점을 시각적으로 확인 |
| 반응형·브랜딩 | 로그인·회원가입·Dashboard·MyPage 반응형 레이아웃과 브랜드·마스코트, 설정 placeholder | 화면 폭과 시연 환경이 달라도 핵심 조작을 유지 |
| Demo 계정·배포 | demo seed 계정, E2E 가상 데이터 정합성, `APP_ENV` 기반 demo 배포 설정 | 발표 환경을 반복 초기화하고 운영 설정과 분리 |

| 검색 모드 | `vector` |
| 법률 지식베이스 | 기록상 36청크 |
| 계정 | 가상 데이터 계정 |

2차 실행 기록에는 비밀값의 존재 여부와 `ruff` 통과가 체크되어 있으나 전체 pytest 통과 수는 기록되지 않았다. 또한 기록에 `demo_seed --reset` 체크가 있으나 Service 메모리는 현재 구현이 `--reset`을 지원하지 않는 idempotent seed라고 설명한다. 두 자료가 정리되기 전에는 해당 체크를 DB 초기화 증적으로 확정하지 않는다.

### 4.4 CI/CD 환경

CI는 다음 세 Job으로 구성된다.

1. Python 테스트와 Ruff
2. 예시 환경 파일을 이용한 배포 자산·Compose 해석 및 배포 스크립트 문법
3. Backend·Frontend 기동, Backend `/health`, Frontend health, 내부 연결을 확인하는 Compose smoke test

CD는 수동 확인 후 preflight, 이미지 병렬 빌드·push, GCP VM 배포, 내부 생성 요청, 외부 healthcheck 순으로 실행된다. 현재 자료에는 이 CD를 실제로 실행한 로그, 외부 healthcheck 응답, 이미지 push 결과가 없다.

## 6) Discussion - 결과 해석과 한계

> 회차별로 관찰된 한계와 원인을 나누어 기록한다. 기능 자체의 한계와 해당 회차에서
실행하지 못한 범위를 혼동하지 않도록 구분한다.

### 6.1 1차 실행에서 확인된 한계

| 대상 | 관찰된 현상 | 해석 및 보완 방향 |
| --- | --- | --- |
| C01 | Consultant의 불법 입력이 차단 종료가 아니라 전략 응답으로 진행됨 | Consultant의 `check_input` 결과를 종료 상태로 변환하는 routing 확인 필요 |
| C02 | 과장 표현 대안이 안정적으로 재현되지 않음 | 고정 위험 카피 fixture 또는 규제 노드 주입으로 대안 표시를 반복 검증해야 함 |
| C04~C05 | Basic은 재질문·후속 생성이 동작했으나 Consultant 경로는 기대대로 진입하지 않음 | 챗봇별 정보 부족 계약과 후속 입력 범위를 분리해 명시해야 함 |
| C06 | 잔액 부족 메시지는 보였으나 충전 화면 이동은 확인되지 않음 | 402 응답과 `충전하기` CTA callback 연결을 확인해야 함 |
| C07~C08 | 독립 장애 주입 경로가 없어 실행하지 못함 | timeout·Provider 오류·부분 실패를 재현할 테스트 double 필요 |
| D01 | 동일 UI 입력을 다시 제출할 때 무료 사용량 차감이 관찰됨 | 네트워크 재시도 멱등성과 사용자의 의도적 재생성 정책을 분리해 결정해야 함 |
| D02 | 새로고침 후 진행 중 생성 복구·재시도 안내가 확인되지 않음 | pending 식별자 저장 또는 서버 조회 기반 복구 계약이 필요함 |
| F02 | `연말` 질문에 자동 계절성인 여름·8월 표현이 섞임 | 명시적 시점 우선 규칙을 출력 후에도 검증해야 함 |
| F03 | 응답 `sources`에서 Trend 근거가 확인되지 않음 | keyword 추출, Trend 호출 결과, 최종 sources를 함께 기록해야 원인을 좁힐 수 있음 |
| F04 | Trend만 실패시키는 실행 경로가 없어 실행하지 못함 | 외부 API 의존성을 테스트 double 또는 dependency override로 분리해야 함 |

### 6.2 2차 실행에서 확인된 한계

| 대상 | 관찰된 현상 | 해석 및 보완 방향 |
| --- | --- | --- |
| B06~B09·F08 | Consultant→Basic 연계 흐름을 해당 회차에서 실행하지 못함 | 테스트 범위의 Blocked이며 영구 기능 한계로 해석하지 않음. 최종 시연 환경에서 연계 흐름을 재확인해야 함 |
| C02 | 결과표에는 정상 동작이 기록됐지만 재현 가능한 과장 표현 선택 케이스는 부족함 | 고정 fixture가 없으면 대안 문구 UI를 반복 검증하기 어려움 |
| C04~C05 | Basic 재질문은 기록됐고 Consultant에 같은 계약을 적용할지는 별도 확인 대상임 | 챗봇별 계약 차이를 결과표에 명시해야 함 |
| C06 | 크레딧 부족 메시지는 있으나 `충전하기` CTA가 없음 | 서버 402와 결제 화면 전환의 Frontend 연결이 남은 과제임 |
| C07 | Provider 장애와 Credit 미소모는 확인했으나 생성 중간 중단·rollback은 확인하지 못함 | 외부 장애와 워커 중단을 별도 시나리오로 분리해야 함 |
| C08 | 일부 proposal 실패 뒤 나머지 표시를 관찰함 | 동일 실패를 독립 재현할 fixture가 필요함 |
| D01 | Basic·Consultant 재실행에서 무료 사용량 차감이 다시 관찰됨 | 새 key를 발급하는 UI 재생성은 Backend 멱등 재시도와 별도 정책임을 명시해야 함 |
| D02 | 새로고침 후 복구·재시도 안내가 관찰되지 않음 | 브라우저·서버 중 어느 쪽이 pending 상태를 소유할지 결정해야 함 |
| F02 | `연말` 질문에 여름·8월 표현이 잔류함 | 프롬프트 지침만으로는 출력 계약이 닫히지 않으므로 후검증이 필요함 |
| F04 | Trend 단독 장애 주입은 여전히 실행하지 못함 | Trend graceful degradation은 미확정 상태로 남김 |

### 6.3 공통 설계·운영상의 개선 방향

Basic 이미지 생성은 카피·이미지 3안을 모두 생성하면서 응답 시간이 길어질 수 있다. 운영 단계에서는 비동기 작업 큐나 별도 추론 워커를 도입해 요청 스레드와 무거운 이미지 생성을 분리하는 방향을 검토할 수 있다. 또한 규제·Trend·부분 실패는 실제 외부 API와 LLM 출력의 변동성이 있으므로, 고정 입력·테스트 double·출력 후검증을 함께 두어야 회차 간 결과를 비교할 수 있다.

## 7) Conclusion - 결론

인증·지오코딩, 사용량·Credit, 생성 오케스트레이션을 순서대로 구현하고 이를 React 화면과 실제 모델 런타임에 연결했다. 이후 결과 승인·이력·결제·지도·X-배너·대기 화면·Demo 배포 설정을 보강해 사용자가 입력하고 생성하고 확인하고 다시 찾는 흐름을 완성했다. Basic과 Consultant 모델은 각자의 그래프·프롬프트·검증 로직을 유지하면서, Service가 공통 요청·응답 계약과 저장·과금 경계를 연결하는 방식으로 통합했다.

1차 로컬 실행과 2차 GCP Demo 실행에서는 회원가입부터 광고 생성·결과·이력까지의 정상 흐름, Consultant 전략 표시, Credit·충전·세션 흐름을 확인했다. 계절성·Trend 검증에서는 기준일 우선 처리와 채널별 결과를 확인했고, 연계 시나리오는 회차별 실행 범위에 따라 확인된 항목과 후속 확인 항목을 구분했다.

이번 작업을 통해 서비스 계약과 모델 결과를 화면·DB·배포 환경까지 연결하는 기반을 마련했다. 앞으로는 Basic 이미지 생성 시간 단축, 규제·Trend 예외 흐름의 재현성, 새로고침 중 생성 복구와 같은 개선을 이어가면 실제 운영에서도 더 안정적인 사용자 경험을 제공할 수 있다.
