## 1. Abstract - 초록

소상공인은 상권 규모, 주변 경쟁점, 검색 관심도처럼 서로 다른 데이터를 함께 해석해야 마케팅 전략을 세울 수 있다. 그러나 공공 API의 원시 수치를 그대로 보여주면 무엇을 해야 하는지 알기 어렵고, 생성형 언어 모델만 사용하면 확인되지 않은 지역 특성이나 할인 수치를 만들어낼 수 있다. 이 프로젝트는 두 문제를 함께 다루기 위해 LangGraph 기반 컨설턴트 챗봇을 설계했다.

챗봇은 사용자 질문을 분석한 뒤 상권 정보, 검색어 트렌드, 추천 후속 질문, 날짜 기반 계절성을 병렬로 준비한다. 상권 데이터는 소상공인시장진흥공단 OpenAPI, 검색 관심도와 연관 검색어는 네이버 API를 사용한다. 외부 API 결과는 Cache-Aside 방식으로 재사용하며, 일부 데이터 조회가 실패해도 남은 데이터로 답변을 만들 수 있게 했다. 최종 응답은 요약, 실행 항목, 근거, 출처, 추천 질문으로 구성된다.

품질 평가는 직접 구축한 골든 데이터셋 60문항으로 수행했다. 규칙 기반 검사는 응답 계약, 허용 범위 밖 숫자 사용, 트렌드 호출 경로를 확인하고, 별도의 LLM Judge는 근거 충실도, 실행 가능성, 구체성, 자연스러움을 1~5점으로 평가했다. fixture를 주입한 최종 평가에서 실패율과 허용되지 않은 숫자 사용률은 0%, 응답 계약 준수율과 트렌드 경로 일치율은 100%였으며 LLM Judge 평균은 4.325점이었다. 콜드 캐시 8건에서는 상권·트렌드·추천 질문 세 I/O 구간의 순차 합산 대비 병렬 실행 시간이 평균 42.8% 감소했다.

모든 개선 시도가 유지된 것은 아니다. 지역 과잉 추론, 무의미한 연관 검색어 사용, 근거 없는 할인율 제안을 프롬프트만으로 막으려 한 실험은 36문항 중 11문항만 기준을 충족해 전면 롤백했다. 이 결과는 정확한 계산이나 사실 판정을 확률적 문장 생성에 맡기는 방식의 한계를 보여준다. 평균 점수보다 데이터 조회, 계약 검사, 품질 평가, 롤백 기준을 같은 개발 절차로 관리할 수 있게 된 점을 결과로 본다.

### 2.2 배경과 문제 정의

소상공인의 마케팅 질문은 짧지만 답변에 필요한 조건은 복합적이다. “이번 달에 어떤 행사를 하면 좋을까요?”라는 질문에는 업종, 위치, 주변 경쟁점, 시점, 홍보할 상품이 함께 고려되어야 한다. 범용 챗봇은 일반적인 아이디어를 빠르게 제시할 수 있지만, 해당 가게와 상권에 맞는 근거를 자동으로 확보하지 못한다. 반대로 공공데이터 API만 연결하면 수치는 얻을 수 있어도 실행 가능한 전략으로 바꾸기 어렵다.

기존 방식과 목표 상태의 차이는 다음과 같다.

| AS-IS | 문제 | TO-BE |
| --- | --- | --- |
| 범용 LLM이 일반적인 홍보 아이디어를 생성 | 가게 위치와 주변 경쟁 상황이 반영되지 않음 | 실측 상권 데이터를 전략 근거로 제공 |
| 모든 질문에 외부 데이터를 일괄 조회 | 대상이 없는 트렌드 조회가 비용과 무관한 근거를 만듦 | 구체 상품·메뉴가 있을 때만 트렌드 조회 |
| 자연어 응답을 사람 눈으로만 확인 | 필드 누락과 허용되지 않은 수치 사용을 반복 검증하기 어려움 | 규칙 검사와 LLM Judge를 분리한 자동 평가 |
| 외부 API 실패가 전체 응답 실패로 이어질 수 있음 | 한 데이터 소스 장애가 상담을 중단 | Cache-Aside와 부분 성공으로 남은 근거를 사용 |

이 프로젝트는 다음 세 가지 문제를 해결 대상으로 정했다.

1. 상권과 트렌드 데이터를 질문에 맞게 선택해 조회할 것.
2. 조회 결과를 소상공인이 바로 시도할 수 있는 행동으로 바꿀 것.
3. 모델이 사용하지 않은 수치나 출처를 근거처럼 제시하지 못하게 할 것.

### 2.3 목표와 요구사항

구현 목표는 “그럴듯한 답변을 생성하는 챗봇”이 아니라 “근거와 실행 항목을 함께 반환하고, 실패 조건을 측정할 수 있는 챗봇”이다. 이를 위해 다음 기준을 설정했다.

- 질문에 구체적인 상품이나 메뉴가 있을 때만 트렌드를 조회한다.
- 외부 API 실패가 전체 상담 실패로 이어지지 않게 한다.
- 응답 형식을 두 챗봇과 서비스가 공유하는 계약에 맞춘다.
- 상권 수치와 출처 사용 여부를 자동 검사한다.
- 생성 모델과 평가 모델을 분리해 모델 변경 효과를 비교할 수 있게 한다.
- 개선이 실측으로 확인되지 않으면 변경을 유지하지 않는다.

이를 구현 요구사항으로 바꾸면 다음과 같다.

| 구분 | 요구사항 | 구현·검증 기준 |
| --- | --- | --- |
| 필수 | 질문에서 트렌드 키워드를 선택적으로 추출 | 기대 경로와 실제 호출 경로 비교 |
| 필수 | 상권·트렌드 조회 실패 시에도 상담 지속 | 실패 데이터는 `None`, 나머지 데이터로 전략 생성 |
| 필수 | 서비스 공용 응답 계약 준수 | 필수 필드와 배열 길이를 규칙으로 검사 |
| 필수 | 근거 없는 수치 사용 억제 | 문항별 `allowed_numbers`와 응답 숫자 대조 |
| 필수 | 입력·출력 보안 검증 연결 | `check_input`, `check_output`, `self_check` 라우팅 테스트 |
| 성능 | 독립 I/O 노드 병렬 실행 | 콜드 캐시에서 순차 환산 시간과 병렬 시간 비교 |
| 평가 | 생성과 채점을 다른 모델로 분리 | 모델별 설정과 토큰 사용량을 결과에 기록 |

### 2.4 연구 질문

개발 결과를 기능 목록이 아니라 검증 가능한 질문으로 연결하기 위해 다음 세 가지 연구 질문을 두었다.

- **RQ1.** 외부 데이터 조회 실패를 허용하면서도 응답 계약과 트렌드 호출 경로를 안정적으로 유지할 수 있는가.
- **RQ2.** 서로 독립적인 I/O 노드를 병렬화하면 해당 구간의 처리 시간이 실제로 줄어드는가.
- **RQ3.** 규칙 검사와 LLM Judge를 분리한 평가가 회귀를 발견하고, 유지할 변경과 롤백할 변경을 구분하는 데 도움이 되는가.

RQ1은 실패율·계약 준수율·트렌드 경로 일치율, RQ2는 콜드 캐시 I/O 시간, RQ3은 60문항 평가와 36문항 롤백 실험으로 확인한다.

### 2.5 범위

컨설턴트 챗봇은 마케팅 전략을 생성하지만 광고 문구 자체는 만들지 않는다. 사용자가 상담 결과에서 “이 전략으로 광고 만들기”를 선택하면 서비스 계층이 저장된 상담 결과를 다시 검증하고 `source_context`로 조립해 기본 챗봇에 전달한다. 따라서 컨설턴트 모델은 기본 챗봇을 직접 호출하지 않으며, 두 모델 사이의 연결은 서비스가 담당한다.

검증 함수도 역할에 따라 구분했다. 컨설턴트 그래프에는 입력 보안 검사, 출력 보안 검사, 응답 자체 검사의 3종을 연결했다. 광고 문구의 표시광고법 위반을 판정하는 규제 검사는 실제 광고 문구를 생성하는 기본 챗봇 경로에서 수행한다.

## 3. Related Work - 관련 접근과 프로젝트 기준선

### 3.1 상태 기반 그래프

LLM 애플리케이션을 하나의 긴 함수나 프롬프트 체인으로 만들면 중간 실패, 조건 분기, 부분 재실행을 분리하기 어렵다. LangGraph는 공유 상태, 노드, 엣지로 워크플로를 구성하는 방식을 제공한다[1]. 이 프로젝트는 질문 분석, 데이터 조회, 전략 생성, 검증을 독립 노드로 나누고, 입력 차단이나 self-check 재시도를 조건부 엣지로 표현했다.

### 3.2 Cache-Aside와 부분 성공

Cache-Aside는 먼저 캐시를 확인하고, 미스일 때 원본 데이터 소스를 조회한 뒤 결과를 캐시에 적재하는 방식이다[2]. 이 프로젝트는 상권·트렌드 API에 같은 패턴을 적용하되 캐시 DB 장애를 원본 API 실패로 취급하지 않았다. 캐시는 지연과 호출량을 줄이는 최적화이며, 상담을 수행하기 위한 필수 의존성은 아니라는 판단이다.

### 3.3 규칙 검사와 LLM Judge의 분리

LLM-as-a-Judge는 자유 형식 응답을 사람 평가보다 적은 비용으로 반복 측정할 수 있지만, 점수 편향과 재현성 한계가 알려져 있다[3]. 따라서 이 프로젝트는 필드 누락, 배열 길이, 허용되지 않은 숫자처럼 기계적으로 판정할 수 있는 항목을 Python 규칙으로 검사하고, 근거 해석과 자연스러움만 Judge에 맡겼다. 공용 규제 검증 파트에서 사용한 RAGAS도 검색 근거의 재현율·정밀도·충실도를 나눠 보는 평가 방식이다[4].

### 3.4 프로젝트 내부 기준선

동일한 60문항을 반복 측정한 v0~v2는 최종 설계의 내부 기준선이다.

| 버전 | 확인된 문제 | 반영한 조치 |
| --- | --- | --- |
| v0 | 실행 실패, 계약 누락, 트렌드 키워드 과대 추출 | 최초 기준선 확보 |
| v1 | 실패는 제거됐지만 혼합 키워드 반례 1건 잔존 | 파싱 복구와 질문 분석 반례 추가 |
| v2 | 계약·트렌드 경로 안정화 필요 | 혼합 키워드 수정, 상권·트렌드 2-way 병렬화 |

### 3.5 기준선에서 얻은 설계 원칙

버전별 결과에서 다음 원칙을 정리했다.

- 평균 점수가 높아도 실행 실패와 계약 누락은 별도로 관리해야 한다.
- 한쪽 반례를 추가하면 반대 방향의 오류가 생길 수 있다.
- 데이터와 프롬프트 조건이 다르면 버전 간 점수를 직접 비교하지 않는다.
- 측정이 변경을 지지하지 않으면 현행 유지나 롤백도 유효한 결과다.
- 정확한 수치 계산과 사실 판정은 자유 생성 프롬프트보다 구조화된 코드에 두는 편이 안전하다.

## 4. Method - 시스템 설계와 구현

### 4.1 전체 구조

최종 컨설턴트 그래프의 처리 순서는 다음과 같다.

```text
사용자 질문
   ↓
입력 보안 검사
   ↓
질문 분석
   ├─ 추천 후속 질문 생성 ─────┐
   ├─ 상권 데이터 조회 ────────┤
   ├─ 트렌드 데이터 조회 ──────┤  병렬 실행
   └─ 날짜 기반 계절성 계산 ───┘
                 ↓
             전략 생성
                 ↓
      전략 품질 단계(빈 노드)
                 ↓
          출력 보안 검사
                 ↓
            응답 자체 검사
                 ↓
              최종 응답
```

`question_analysis`는 질문을 상담에 적합한 형태로 정리하고, 정보 충분성, 누락 정보, 트렌드 검색 키워드를 만든다. 이후 네 노드는 서로의 결과를 사용하지 않으므로 병렬로 실행된다. 네 결과가 모두 준비되면 `strategy`가 이를 하나의 응답으로 조립한다.

`strategy_check`는 그래프에 연결돼 있지만 함수가 빈 딕셔너리만 반환하는 예약 단계다. 최종 범위에서는 구현되지 않았으므로 운영 중 전략 품질을 검사하는 기능으로 계산하지 않는다. 실제 품질 평가는 그래프 밖의 오프라인 평가 스크립트에서 수행한다.

### 4.2 사용자 흐름과 핵심 기능

사용자는 가게를 등록한 뒤 컨설턴트 챗봇에 마케팅 질문을 입력한다. 서비스는 가게의 업종과 좌표를 모델 요청에 포함하고, 컨설턴트 그래프는 질문에 필요한 데이터만 준비한다. 최종 결과는 화면에서 요약·실행 항목·근거·추천 질문으로 표시되며, 사용자는 후속 질문을 이어가거나 해당 전략을 광고 생성 흐름으로 넘길 수 있다.

핵심 기능을 입력·처리·출력으로 정리하면 다음과 같다.

| 기능 | Input | Process | Output |
| --- | --- | --- | --- |
| 질문 분석 | 질문, 가게 업종 | 질문 재작성, 정보 충분성·키워드 판정 | 정제 질문, 누락 정보, 트렌드 키워드 |
| 데이터 준비 | 좌표, 업종, 키워드, 기준일 | 상권·트렌드 조회, 계절성 계산, 추천 질문 생성 | 전략 생성용 `context`와 칩 3개 |
| 전략 생성 | 질문, 가게 정보, 준비된 context | 구조화 프롬프트 호출과 파싱·재요청 | 제목, 요약, 실행 항목, 근거 |
| 검증 | 입력과 전략 응답 | 입력·출력 보안 검사, self-check | 차단·마스킹 또는 최종 응답 |
| 광고 연계 | 저장된 컨설팅 결과 ID | 서비스가 결과를 검증해 `source_context`로 조립 | 기본 챗봇이 사용할 광고 생성 입력 |

### 4.3 기술 구성과 선택 이유

| 기술·데이터 | 적용 지점 | 선택 이유 |
| --- | --- | --- |
| Python 3.11 | 모델·평가 코드 | 팀 모델 코드와 공용 검증 모듈의 실행 환경 통일 |
| LangGraph | 컨설턴트 워크플로 | 조건 분기, 병렬 실행, 재시도 경로를 노드와 엣지로 명시 |
| OpenAI API | 질문 분석, 추천 질문, 전략 생성, Judge | 구조화 JSON 응답과 생성·채점 모델 분리 지원 |
| httpx | 공공·네이버 API 클라이언트 | 타임아웃과 HTTP 예외를 명시적으로 처리 |
| SQLite·SQLAlchemy | 상권·트렌드 캐시 | 팀의 로컬·서비스 환경에서 별도 캐시 서버 없이 재사용 가능 |
| 소상공인시장진흥공단 OpenAPI | 상권 데이터 | 좌표 반경 내 매장과 업종 정보를 공식 데이터로 확보 |
| 네이버 API HUB·검색광고 API | 트렌드·연관 검색어 | 구체 상품에 대한 검색 관심 방향과 연관어 확보 |
| pytest·Ruff | 회귀 검증·정적 검사 | 노드 계약과 그래프 경로를 자동 검증하고 코드 품질을 통일 |

기술은 기능 수를 늘리는 기준이 아니라 실패 지점을 분리할 수 있는지를 기준으로 선택했다. LangGraph는 데이터 조회 네 갈래를 병렬화하고, 검증 실패 시 필요한 노드만 재실행하는 구조를 코드로 드러낸다. Cache-Aside는 외부 API를 대체하지 않고 호출량과 지연을 줄이는 역할만 맡는다.

### 4.4 질문 분석과 조건부 트렌드 조회

모든 질문에서 트렌드 API를 호출하지 않는다. “아이스라테 신메뉴 홍보 전략”처럼 구체적인 상품이나 메뉴가 있으면 `keyword="아이스라테"`를 추출해 트렌드 경로를 연다. “매출을 늘리려면?”처럼 대상이 없는 질문은 `keyword=None`으로 처리하고 트렌드 API를 호출하지 않는다.

이 기준은 비용 절감만을 위한 것이 아니다. 검색할 대상이 없는데 트렌드 데이터를 억지로 붙이면 질문과 관계없는 검색어가 답변 근거로 사용될 수 있다. 골든 데이터셋은 트렌드 미사용 문항 45개와 사용 문항 15개를 분리해 이 경로를 확인한다.

### 4.5 상권 데이터 계층

상권 조회는 소상공인시장진흥공단 상권정보 OpenAPI의 반경 내 상가업소 조회를 사용한다. 반환 정보는 다음 네 항목으로 제한한다.

- 반경 내 전체 매장 수.
- 동일 업종 매장 수.
- 가장 가까운 동일 업종 매장까지의 거리.
- 업종 분포 정보.

업종은 가능한 경우 검증된 소분류 코드를 사용한다. 매핑이 없는 업종은 텍스트 매칭으로 폴백한다. API의 한 페이지 최대 건수로 인해 일부 세부 집계가 첫 페이지에 한정될 수 있으므로, 전체 매장 수와 세부 집계의 의미를 구분했다.

상권 캐시 키는 위도와 경도를 소수 셋째 자리로 반올림해 만든다. 캐시를 먼저 조회하고, 만료되었거나 값이 없으면 API를 호출한 뒤 결과를 저장한다. 상권 데이터 TTL은 7일이다. API 키가 없거나 요청이 실패하면 `None`을 반환하며, 이 실패만으로 상담 전체를 중단하지 않는다.

### 4.6 트렌드 데이터 계층

검색 관심도는 네이버 API HUB, 연관 검색어는 네이버 검색광고 API를 통해 준비한다.

- 조회한 키워드.
- 최근 검색 관심도의 방향인 상승·하락·유지.
- 연관 검색어.

트렌드 캐시도 TTL 7일의 Cache-Aside 구조를 사용한다. 검색 관심도는 최근 30일을 전반 2주와 후반 2주로 나누어 비교하고, 변화율 10%를 기준으로 방향을 판정한다. 18개 키워드 실측과 30일·60일 창 비교에서 기간을 늘리면 계절 곡선의 서로 다른 구간이 섞여 방향이 뒤집히는 사례가 확인되어 30일 창을 유지했다.

연관 검색어는 모델 입력에 제공할 수 있지만, 문자열이 그럴듯하다는 이유만으로 실제 마케팅 소재로 쓰일 위험이 있다. 별도 의미 판정 단계가 없는 현재 구조에서는 방향 정보를 중심으로 사용하고, 노이즈 가능성이 있는 연관어는 제한적으로 취급한다.

### 4.7 날짜 기반 계절성

날씨 API는 최종 범위에서 제거했다. 광고 전략은 특정 시각의 날씨보다 월과 계절의 영향을 더 길게 받을 수 있고, 날씨 API를 추가하면 비용과 장애 지점이 늘어난다. 대신 KST 기준 날짜로 봄·여름·가을·겨울과 월 상순·중순·하순을 계산하는 순수 함수를 공용 계층에 두었다.

운영에서는 기준일을 주지 않으면 KST의 오늘을 사용한다. 평가에서는 `VALIDATION_REFERENCE_DATE` 또는 문항별 고정 기준일을 사용해 같은 입력이 같은 계절 조건을 보게 한다. 계절성은 외부 데이터가 아니므로 `sources`에 넣지 않는다. 근거에는 “8월 하순, 요청일 기준”처럼 달력 사실만 사용할 수 있고, 날짜만 보고 수요가 증가한다고 단정하지 않는다.

### 4.8 전략 생성과 응답 계약

전략 생성 모델은 다음 형식을 반환한다.

| 필드 | 역할 |
| --- | --- |
| `title` | 상담 결과 제목 |
| `strategy.summary` | 핵심 전략 요약 |
| `strategy.actions` | 1~3개의 실행 항목 |
| `reasons` | 상권·트렌드 등 실제 사용 근거 |
| `sources` | 조회에 성공해 전략 생성에 제공한 외부 데이터 출처 |
| `suggested_chips` | 사용자가 이어서 물어볼 질문 3개 |

`sources`는 상권·트렌드 조회에 성공해 전략 생성 입력으로 제공한 데이터 출처를 기록한다. 이 필드만으로 모델이 해당 데이터를 문장에서 실제 활용했다고 단정하지 않으며, 실제 활용 여부는 `reasons`와 근거 충실도 점수로 평가한다. 트렌드 조회가 실패했거나 질문에 키워드가 없어 호출하지 않았다면 “트렌드”를 넣지 않는다. 계절성은 계산값이므로 출처 목록에 포함하지 않는다.

실행 항목이 형식에 맞지 않으면 한 번 재요청하고, 여전히 3개를 초과하면 앞의 3개만 사용한다. 파싱 실패를 숨기지 않기 위해 실패 사유를 `actions_not_list`, `actions_wrong_length`, `invalid_type`, `missing_content`로 구분해 기록한다.

### 4.9 추천 질문 생성과 방향 검사

추천 질문은 사용자가 다음 대화를 시작할 수 있는 문장 3개다. 초기 프롬프트는 누락 정보를 “채우는 질문”으로 만들라고 지시해 “타겟 고객층은 누구인가요?”처럼 챗봇이 사용자에게 되묻는 방향의 문장을 생성했다.

프롬프트를 사용자 관점으로 고치고 금지·허용 예시를 추가했다. 어미가 `-까요?` 또는 `-주세요`인지 검사하는 규칙 필터도 시험했지만, “효과적인 마케팅 채널은 무엇인가요?” 같은 정상 문장을 오탐해 10문항 중 5문항을 폴백시켰다. 해당 필터는 제거하고, 생성 프롬프트와 별도의 화자 방향 평가로 방어선을 옮겼다.

### 4.10 검증 함수 연결

공용 검증 함수는 네 종류지만 컨설턴트가 사용하는 것은 세 종류다.

| 검증 함수 | 컨설턴트 적용 | 처리 |
| --- | --- | --- |
| `check_input` | 적용 | 프롬프트 인젝션·불법 요청을 LLM 호출 전에 차단 또는 재질문 |
| `check_regulation` | 미적용 | 광고 문구 전용. 기본 챗봇에서 수행 |
| `check_output` | 적용 | 민감정보 노출을 차단하거나 마스킹 |
| `self_check` | 적용 | 근거와 완결성을 검사하고 필요하면 전략을 한 번 재생성 |

검증 함수 내부는 PM 담당 영역이며 컨설턴트 코드는 반환값을 상태와 라우팅으로 변환한다. 입력 차단은 질문 분석 이전에 종료되고, 출력 차단은 결과를 폐기한다. `self_check`의 `reject`는 전략 노드만 한 번 다시 실행하므로 상권·트렌드 API와 추천 질문 LLM을 반복 호출하지 않는다.

### 4.11 상담 결과의 광고 생성 연계

컨설턴트는 기본 챗봇을 직접 호출하지 않는다. 상담 응답은 서비스 DB에 저장되고, 사용자가 나중에 광고 생성 버튼을 누르면 서비스가 `source_gen_id`로 결과를 조회한다. 서비스는 저장된 `summary`, `actions`, `reasons`, `sources`를 다시 검증해 `source_context`로 조립하고 기본 챗봇 요청에 넣는다.

이 경계를 고정하기 위해 정상 왕복 1건과 잘못된 `sources`, `reasons`, `actions` 4건을 포함한 계약 테스트를 작성했다. 프론트엔드 버튼 구현과 관계없이 모델·저장·복원 계약은 독립적으로 확인할 수 있다.

## 5. Experiment Setup - 실험 및 평가 환경

### 5.1 개발 환경

| 항목 | 환경 |
| --- | --- |
| 언어 | Python 3.11 |
| 그래프 | LangGraph 1.2.10 |
| LLM SDK | OpenAI Python SDK 2.54.0 |
| HTTP | httpx 0.28.1 |
| 저장소 | SQLite, SQLAlchemy 2.0.51 |
| 테스트 | pytest 8.4.2 |
| 정적 검사 | Ruff 0.16.1 |

평가는 외부 상권·트렌드 API 응답을 fixture로 고정한 로컬 실행 환경에서 수행했다. 생성 모델과 Judge만 실제 OpenAI API를 호출했다. 이 구분은 외부 데이터의 일시적 변화와 생성 모델의 변화를 섞지 않기 위한 것이다.

### 5.2 골든 데이터셋과 전처리

컨설턴트 평가 데이터셋은 60문항으로 구성했다.

| 구분 | 구성 |
| --- | --- |
| 질문 유형 | 상권 20, 전략 27, 시즌·이벤트 13 |
| 업종 | 카페 14, 치킨 16, 미용실 15, 슈퍼마켓 15 |
| 상권 fixture | F1~F8, 실측 스냅샷 8종 |
| 트렌드 경로 | 구체 키워드 포함 15문항, 미포함 45문항 |
| 계절 분포 | 봄·여름·가을·겨울 각 15문항 |

각 문항은 질문, 가게 정보, 상권 fixture, 필요 시 트렌드 fixture, 예상 계약, 허용 숫자, 평가 rubric을 가진다. 상권과 트렌드 fixture는 실제 API에서 측정한 값을 고정한 스냅샷이다. 자동 재수집으로 값을 교체하지 않고 측정일과 버전을 기록한다.

`industry_breakdown`은 fixture에 보존하지만 전략 프롬프트에는 넣지 않는다. 공공 API의 페이지 상한 때문에 전체 분포로 오해될 수 있기 때문이다. 따라서 환각 검사에 쓰는 `allowed_numbers`에서도 해당 파생 숫자를 제외한다.

평가 전처리는 세 단계다. 첫째, 질문이 특정 상품을 포함하는지에 따라 `trend_fixture` 사용 여부를 명시한다. 둘째, API 응답 중 전략에 제공할 필드만 추려 그래프의 실제 반환 계약과 맞춘다. 셋째, 응답에서 허용할 수치를 문항별 `allowed_numbers`에 기록한다. 이 과정으로 데이터 누락과 “조회하지 않은 값을 모델이 만들어낸 경우”를 구분한다.

### 5.3 모델과 실행 조건

| 항목 | 값 |
| --- | --- |
| 생성 모델 | `gpt-4o-mini` |
| 생성 temperature | 0.3 |
| Judge 모델 | `gpt-4.1-mini` |
| Judge temperature | 0.0 |
| 데이터셋 버전 | `v1.3-seasonality-4season` |
| 상권 fixture 버전 | `v2-industry-code` |
| 트렌드 fixture 버전 | `v2-no-weather` |
| 평가 문항 수 | 60 |

생성 모델과 Judge 모델을 분리했다. 두 모델을 동시에 바꾼 결과는 원인을 구분할 수 없으므로 직접 비교하지 않는다. 평가 스크립트는 문항을 직렬로 실행하고 요청 사이에 대기 시간을 둔다. 상권·트렌드 호출은 fixture로 대체하고, 실제 OpenAI API는 전략 생성과 Judge 채점에만 사용한다.

`gpt-4o-mini`는 운영 모델과 평가 대상 모델을 같게 유지하면서 비용을 통제하기 위해 선택했다. Judge는 생성 모델과 다른 `gpt-4.1-mini`로 고정해 생성 품질 변화와 채점 기준 변화를 분리했다. 질문 분석과 전략 생성은 구조화된 JSON을 주고받고, Judge는 네 평가축의 정수 점수와 판단 근거를 반환한다.

### 7.2 결과 해석

v0의 Judge 평균은 4.39점으로 최종 v3보다 높았다. 그러나 v0는 60문항 중 5문항에서 그래프 실행이 실패했고 계약 준수율도 91.7%였다. 일부 문장의 표현 점수가 높더라도 요청이 정해진 계약으로 끝나지 않으면 서비스가 결과를 사용할 수 없다. 따라서 이번 개발에서 우선 확인할 성과는 Judge 평균의 소폭 변화보다 실패율 8.3%를 0%로 낮추고 계약과 트렌드 경로를 100%로 만든 것이다.

프롬프트 규칙은 구조적 검증을 대체하지 못했다. G 실험에서 금지 지시는 `reasons`에는 적용됐지만 `actions`에서는 반복적으로 우회됐다. 반대로 추천 질문 어미 필터는 정상 문장을 오탐했다. 할인 상한처럼 산술이 필요한 값은 구조화된 입력과 Python 계산으로 옮기고, 지역 특성이나 연관어의 사실성은 승인된 데이터가 없으면 사용하지 않는 편이 안전하다.

| 60문항 평가가 280,909토큰 사용 | 반복 평가 비용 증가 | 변경 유형별 소규모 파일럿 후 전체 평가 승인 절차 유지 |

### 7.4 협업 경계와 결과 귀속

컨설턴트 담당은 그래프, 상권·트렌드 저장소, 전략·추천 질문, 60문항 골든 데이터셋과 평가기를 구현했다. 공용 검증 함수 내부와 67문항 거부 평가는 PM·검증 담당 영역이며, 컨설턴트는 공개 계약을 통해 세 함수를 연결했다. 광고 생성 연계도 서비스가 `source_gen_id`를 검증하고 `source_context`를 조립하는 구조로 분리했다.

이 경계는 중복 호출과 소유권 충돌을 줄였지만, 계약 변경이 여러 담당 작업본에 늦게 전파되면 실제 함수 시그니처와 mock 테스트가 어긋날 수 있었다. 이후 `autospec` 기반 테스트와 왕복 계약 테스트를 추가한 이유다. 협업에서 문서 합의만큼 실제 호출부를 검증하는 테스트가 중요하다는 점을 확인했다.

### 7.5 운영 판단

운영 경로에서는 캐시와 부분 성공 처리가 외부 API 호출량과 장애 영향을 줄인다. 반면 병렬화 후 한 노드가 실패해도 이미 시작된 다른 API 호출 비용은 발생한다. 현재 호출량에서는 응답시간 이득을 우선했지만, 트래픽이 증가하면 취소 전파와 호출 예산을 다시 검토해야 한다.

평가도 같은 원칙을 적용했다. 모델과 fixture 버전을 고정하고, 작은 파일럿으로 스키마와 실패 유형을 먼저 확인한 뒤 전체 60문항을 실행했다. 이 절차는 점수 생산 자체보다 비교 가능한 기준선을 남기는 데 목적이 있다.

## 8. Conclusion - 결론

이번 작업은 상권과 트렌드 데이터를 전략 문장에 붙이는 기능에서 출발했지만, 최종적으로는 데이터 조회부터 계약 검사와 평가까지 하나의 흐름으로 구성했다. 골든 데이터셋 범위에서 실패율 0%, 계약 준수율과 트렌드 경로 일치율 100%를 확보했고, 세 I/O 구간의 병렬 실행 시간은 순차 환산 대비 평균 42.8% 줄었다. 다만 Judge 평균은 조건이 다른 버전끼리 단순 비교하지 않고 최종 기준선 4.325점으로 남겼다.

가장 크게 배운 점은 LLM 품질 개선이 프롬프트 문구를 계속 추가하는 작업과 같지 않다는 것이다. 36문항 반례 실험에서 규칙이 실행 항목을 통제하지 못했고, 추천 질문 필터는 정상 문장을 오탐했다. 두 변경을 롤백하면서 “코드를 많이 남기는 것”보다 실패를 재현하고 제거할 근거를 남기는 것이 더 중요하다고 판단했다.

기술적으로는 LangGraph의 상태와 조건부 엣지로 부분 실패와 재시도 범위를 분리하는 방법을 익혔다. 평가 측면에서는 계약·숫자·경로처럼 정답이 명확한 항목은 코드로, 구체성과 자연스러움처럼 해석이 필요한 항목은 Judge로 나누는 편이 결과를 설명하기 쉬웠다. 협업 측면에서는 공용 함수와 서비스 연계의 소유권을 먼저 정하고, 문서 계약을 실제 왕복 테스트로 잠가야 동시 개발 과정의 회귀를 줄일 수 있다는 점을 확인했다.

아쉬운 점은 업종과 지역 범위가 제한적이고, 비수치 과잉 추론을 운영 중에 직접 검사하지 못한다는 것이다. 후속 작업에서는 사용자 명시 시점을 구조화해 계절성 라우팅을 결정하고, 산술은 Python 코드로 옮기며, 공식 출처가 합의된 뒤 업종·지역 벤치마크를 확장하는 순서가 적절하다. 다음 프로젝트에서도 기능을 추가하기 전에 비교 조건과 폐기 기준을 먼저 정의하는 방식을 적용할 것이다.
